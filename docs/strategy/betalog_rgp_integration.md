# BetaLog — Rock Gym Pro Integration & Retention Strategy

How BetaLog connects to a climbing centre's Rock Gym Pro (RGP) system, and how that
connection is used to solve the problems the centre actually cares about: keeping
customers after their first visit, rewarding the ones who stay, and creating new
revenue from coaching and upsell.

This is the approach doc. It covers what the RGP API can and cannot do, the
recommended architecture for getting RGP data into Firestore, the retention and
revenue features that data unlocks, and the privacy obligations that come with it.

Related docs: `betalog_vision.md` (product strategy), `betalog_partner_overview.md`
(gym-facing pitch), `betalog_data_model.md` (canonical schema).

Last updated: 2026-07-02

## 1. The App Today, Through a Centre's Eyes

An honest review of where BetaLog stands as a product a climbing centre would deploy.

### What's genuinely strong

- **Logging depth no booking system has.** Boulder/lead/toprope with outcomes and
  attempts, gym training, hangboard protocols, cardio, weight, health. A centre's
  RGP install knows *that* a member visited; BetaLog knows *what they did* and
  *how they're progressing*. That difference is the entire value of the integration.
- **Offline-first PWA.** Works inside a wall with no signal, installs from a link,
  no app store friction. Right distribution model for a gym handing it to members
  at the front desk.
- **Grade progression, streaks, levels, friends.** The motivational loop —
  progress you can see, friends to compare with — is exactly the mechanic that
  makes a casual first-timer become a regular. It exists and works today.
- **AI coach on real data.** Four personas analysing actual session history.
  Unique in the space; becomes far stronger with gym context (routes, resets).
- **The gym-side design work is done.** Route board, wall map, setter tools,
  multi-centre Firestore structure are all specced (`betalog_vision.md`,
  `betalog_data_model.md`). Nothing about an RGP integration conflicts with them —
  it slots into the same `gyms/{gymId}` tree.

### What's missing for a centre deployment

- **No location on sessions yet.** `session.location` is still a planned bridge.
  Without it, BetaLog can't attribute a session to the centre at all — this is
  the single most important prerequisite and needs no RGP API to build.
- **No backend.** The app is pure client + Firestore on the Spark plan. An RGP
  integration *requires* a server-side component (section 4) because API
  credentials cannot live in the client.
- **No gym admin surface.** The planned `/admin` route is specced for BetaLog's
  own ops, not for gym staff. Retention dashboards for the centre need a staff-
  facing view (can start as a simple role-gated page, same pattern as setter role).
- **Onboarding drop-off.** The 2026-05-29 Firestore audit found 53% of sign-ups
  bounced without logging anything. Before BetaLog can be a gym's retention tool,
  its own first-session experience has to hold new users — a guided "log your
  first climb" flow matters more to the gym pitch than any API.
- **Groq key friction.** The AI coach requiring a user-supplied API key is fine
  for enthusiasts, a dead end for a gym's casual members. A gym-tier offering
  should include a proxied, gym-branded coach (also needs the same server-side
  component — one worker can do both jobs).

**Bottom line:** the member-facing product is strong enough to pilot. The gap is
entirely on the plumbing side — location stamping, a small backend, and a staff
view — and the RGP integration is the reason to build that plumbing now.

## 2. What the RGP API Actually Provides

Grounded in the public API (api.rockgympro.com) and open-source client
implementations. Verify against current docs when the pilot gym grants a key —
RGP evolves and the docs sit behind their support portal.

### The facts

| Aspect | Reality |
|---|---|
| Style | REST, JSON, **read-only** |
| Auth | HTTP Basic Auth — `api-user` + `api-key` generated by the gym (RGP Cloud dashboard, or locally hosted RGP settings) |
| Facilities | `GET /v1/facilities` — the gym's location codes (a multi-centre operator has one code per centre — maps 1:1 to BetaLog's `centreId`) |
| Check-ins | `GET /v1/checkins/facility/{code}` — filterable **by check-in datetime only**; the core stream for everything in this doc |
| Customers | `GET /v1/customers/{id}` — **no bulk listing**; customer records are reached via check-ins/bookings that reference them |
| Bookings | `GET /v1/bookings/...` — filter by created date; **cannot** filter by cancellation date (must re-poll to detect cancellations) |
| Invoices | `GET /v1/invoices/...` — billing records; useful for membership-type signals, avoid syncing amounts |
| Webhooks | **None.** Event-driven flows exist only via RGP's Zapier integration (which itself polls). Native approach: poll on a schedule |
| Writes | **Not possible.** BetaLog cannot create discounts, bookings, notes, or anything else inside RGP |

### What the limitations mean for the design

1. **Polling, not events.** A scheduled sync (every 10–15 min is plenty; check-in
   nudges don't need to be instant) rather than real-time push.
2. **Redemption is analogue.** Because we can't write into RGP's POS, rewards are
   redeemed as *codes shown in the app, validated by staff at the desk* — the gym
   pre-creates matching discount/promo items in RGP themselves. This is fine in
   practice and keeps staff in control.
3. **Customer sync is incremental.** We learn about customers as they check in.
   That's actually aligned with data minimisation (section 7): BetaLog never
   holds the gym's full member database, only members who have appeared in the
   sync window plus those who linked their account.
4. **Cursor state matters.** Check-in polling needs a persisted watermark, and
   (per open-source client experience) should overlap the previous window by a
   few hours to avoid missing late-written rows. Timezone handling is
   under-documented — normalise everything to UTC on ingest and confirm against
   real data during the pilot.

## 3. What the Integration Is For

The centre's stated priorities, mapped to what check-in + performance data enables.

### Priority 1 — Retention after the first visit

The brutal industry pattern: most first-time visitors never come back, and the
gym has no channel to them beyond a marketing email. The RGP integration attacks
this at the exact moment it's winnable:

**The first-visit journey.**
1. New customer appears in the check-in stream flagged as first-time (no prior
   check-ins). The gym's front desk already hands out a "get the app" card / QR
   code with a gym invite link — RGP data tells us whether they actually visited.
2. In the app, a first-timer at the linked centre gets a **beginner journey**,
   not a blank dashboard: "log your first climbs" (three taps), "here's what V0–V2
   feels like", a visible **first-5-visits progress card** with a reward at the
   end (gym-funded: free shoe rental, café coffee, guest pass — section 5).
3. Because sessions are stamped with the centre, the app can honestly say
   "you've been twice — climbers who come 5 times in their first month are the
   ones who get hooked" and show exactly what improved between visits. Generic
   fitness apps cannot do this; a booking system cannot do this.
4. If the check-in stream shows no return visit within N days, the *gym's* CRM
   (not BetaLog) sends the win-back — BetaLog surfaces the at-risk list to staff
   (section 6). BetaLog nudges in-app; the gym nudges by email. Clean separation,
   cleaner GDPR.

**Why linking beats either system alone:** RGP knows about the 100% of first-timers
(everyone checks in); BetaLog converts the ones who install into people with a
visible progress streak to protect. The overlap report — "of 200 first-timers last
month, 60 installed, 41 of those returned vs 22 of the non-installers" — is the
retention evidence the gym pays for.

### Priority 2 — Ongoing retention: gifts, benefits, recognition

Covered fully in section 5. Short version: BetaLog computes milestones from data
it uniquely has (visits × performance × streaks), the gym attaches real-world
rewards, the app handles display and redemption codes, staff validate at the desk.

### Priority 3 — Revenue beyond the door

Covered in section 6. Coaching upsell driven by plateau detection is the standout:
BetaLog can see a member stuck at V4 for ten sessions in a way no other system can,
and "book a session with our coach" is a message that lands *because* it's specific.

## 4. Architecture — RGP → Firestore

### The constraint that shapes everything

The RGP API key grants read access to the gym's **entire member database** —
names, emails, check-in history. It must never ship in the client bundle or be
callable from the browser. BetaLog currently has no server. So the integration's
first deliverable is a small server-side sync component.

### Recommended: Cloudflare Worker sync service

BetaLog already deploys on Cloudflare Pages, so a Worker is the native choice:

```
RGP API  ──(cron poll, Basic Auth)──►  Cloudflare Worker  ──(service acct, REST)──►  Firestore
                                            │
                                   secrets: RGP api-user/key,
                                   Firebase service account
```

- **Cron Triggers** (free tier includes them): every 15 min pull
  `checkins/facility/{code}` from the stored watermark minus a safety overlap;
  nightly pull of bookings + membership-status refresh.
- **Writes to Firestore via the REST API** with a Firebase service account
  (the Admin SDK doesn't run on Workers, the REST path does; sign a JWT for a
  Google OAuth token — well-trodden pattern).
- **Secrets live in Worker environment** — never in the repo, never in the client.
- **Keeps Firebase on Spark.** No Blaze upgrade, no Cloud Functions billing
  surface. Sync volume for a busy centre (~300–500 check-ins/day) is trivial
  for both Worker and Firestore free tiers.
- Bonus: the same Worker later fronts a **gym-funded Groq proxy** for the
  AI coach (removes the user-supplied-key friction for gym members) — one
  backend component, two jobs.

### Alternatives considered

| Option | Verdict |
|---|---|
| Client calls RGP directly | **Rejected.** Exposes the gym's member DB to anyone who opens dev tools. Non-negotiable. |
| Firebase Cloud Functions (scheduled) | Works, but forces Blaze plan and splits infra across two providers' billing. Reasonable fallback if Worker→Firestore auth proves painful. |
| Zapier (RGP's own integration route) | OK for a two-week smoke test ("new check-in → append row"), but per-task pricing scales badly with check-in volume and transforms are weak. Not the platform answer. |

### Firestore shape (extends the existing `gyms/` tree)

```
gyms/{gymId}/
  rgp/
    config                     # server-only: facility-code ↔ centreId map, sync watermarks
                               # (API credentials stay in Worker secrets, NOT here)
  members/{rgpCustomerId}      # server-written, minimised member record:
    emailHash                  # SHA-256 of lowercased email — for linking, not contact
    firstCheckinAt             # ISO datetime
    lastCheckinAt              # ISO datetime
    checkinCount30d            # rolling counter, recomputed by sync
    checkinCount90d
    membershipType             # "member" | "payg" | "punch" | ... (from invoices/customer)
    linkedUid                  # BetaLog user UID once linked, else null
    riskFlag                   # "new" | "active" | "cooling" | "lapsed" (derived, section 6)

users/{uid}/
  gymLinks/{gymId}             # user-side consent record:
    rgpCustomerId, centreId, linkedAt, consentVersion
```

**Rules:** `gyms/{gymId}/rgp/*` and `members/*` are readable only by gym staff
(admin role) and the server; a linked user may read *their own* member doc
(`linkedUid == request.auth.uid`). Members never see other members' RGP data.

Check-in *events* don't need to be stored individually in Firestore for v1 —
the rolled-up counters and timestamps on the member doc cover every feature in
this doc, and it keeps document counts (and PII surface) small. Raw event
retention can come later if analytics demand it.

### Member linking — consent-first

The join between an RGP customer and a BetaLog account is the hinge of the whole
integration, and it must be opt-in:

1. Member taps **"Link my [gym] membership"** in Settings (or from the gym
   invite link at onboarding).
2. App sends the member's verified auth email (hashed) to the Worker; Worker
   matches against `emailHash` on synced member docs.
3. Match → write `linkedUid` + the user-side `gymLinks` doc, showing the member
   exactly what linking enables (visit streaks, rewards, and *what the gym can
   see* — aggregate progress only, never session details, per the privacy spec).
4. No match (different email at signup) → fallback: member enters the email
   they gave the gym; Worker verifies with a one-time code to that address, so
   you can't link someone else's membership by guessing their email.

Never auto-link silently. The link screen is also where reward-programme T&Cs
and the gym's privacy notice live.

## 5. The Rewards & Benefits Engine

The generic mechanism that turns milestones into gym-funded perks.

### Model

```
RewardProgramme (per gym, staff-configured)
  trigger:   visit-count | visit-streak | first-N-visits complete |
             grade milestone | challenge complete | comeback (lapsed member returns)
  reward:    free text ("Free shoe rental") + optional RGP promo code reference
  audience:  everyone | first-timers | members only | lapsed
  window:    always-on | date-bounded (e.g. January comeback campaign)

RewardGrant (per member)
  programmeId, uid, earnedAt, code (short redemption code), status: earned | redeemed | expired
```

### Flow

1. **Earn** — the sync Worker (visit-based triggers) or the client (performance
   triggers, verified server-side later) creates a `RewardGrant`. Member gets an
   in-app celebration + the code on their profile.
2. **Redeem** — member shows the code at the desk. Staff validate in a
   one-screen staff view (enter/scan code → shows member name, reward, status →
   tap Redeem). Because the RGP API is read-only, the actual discount is applied
   in RGP's POS by staff using a pre-created promo item — BetaLog records the
   redemption, RGP records the transaction. Reconciliation is the monthly report.
3. **Report** — gym dashboard: grants, redemptions, and the retention delta of
   participants vs non-participants.

### Programme ideas to pitch (gym picks 2–3, not all)

| Programme | Trigger | Why it works |
|---|---|---|
| First Five | 5 visits in first month | Attacks the first-visit cliff directly; reward at visit 5 = free session/rental |
| Streak keeper | 4-week visit streak | Protectable streaks are the strongest habit mechanic in the app already |
| Grade breaker | First V3 / first 6a lead | Celebrates the moment climbing "clicks"; pairs naturally with a coaching taster |
| Comeback | Lapsed 30+ days, returns | Win-back with warmth instead of discount-spam |
| Circuit finisher | Complete a set circuit (route board, Phase 2+) | Ties rewards to the wall itself once routes are live |

Rewards should be *experiential and cheap for the gym* (rental, café item, guest
pass, priority booking for resets) rather than membership discounts — discounts
train members to wait for discounts.

## 6. Revenue Options for the Centre

### Coaching, driven by performance data

The strongest new-revenue story, because it's built on data only BetaLog has:

- **Plateau detection.** Member logged 10+ sessions over 8 weeks with no grade
  movement → in-app card: "Stuck at V4? A one-hour session with [gym]'s coach
  usually breaks it. Book at the desk / [booking link]." Specific beats generic;
  this converts because it arrives at the moment of frustration.
- **Style-gap flags.** Send-rate by discipline/section (richer once the route
  board exists): "strong on overhangs, slab is holding your grade back —
  [coach] runs a footwork clinic Tuesdays."
- **First-timer → course funnel.** The first-visit journey's natural end-state
  for rope climbers is "book the learn-to-lead course"; for boulderers,
  "improver session". The journey card is a standing ad slot the gym controls.
- **Measurement.** RGP's bookings endpoint shows whether coached members book
  again and whether their check-in frequency rises after coaching — the ROI
  report that keeps the gym paying for the Pro tier.
- **Coach visibility (opt-in).** A member can share their BetaLog progression
  with the gym's coach before a session — the coach walks in knowing the
  member's actual history. Better session, better reviews, more rebooking.

### Membership and spend upsell

- **PAYG → membership prompt.** Check-in data shows a pay-per-visit customer
  coming 6+ times/month → app shows the arithmetic: "you'd have saved £X with
  membership this month." The gym sets the thresholds and copy.
- **Quiet-hours nudges.** Aggregate check-in patterns identify dead periods;
  gym attaches off-peak perks ("log a session before 4pm, coffee's on us").
- **Retail moments.** 50 sessions logged → shoe-fitting offer. Light touch,
  clearly gym-branded, never third-party ads.

### The at-risk list (staff-facing)

Derived `riskFlag` per member from check-in cadence: personal-baseline drop
(e.g. 8/month → 2/month) → `cooling`; nothing in 30+ days → `lapsed`. Staff
dashboard shows the list with last visit, tenure, and (if linked) last grade
milestone — armed with which, the gym's own email/CRM does the outreach.
BetaLog deliberately does **not** email non-users on the gym's behalf: BetaLog
nudges people in the app; the gym contacts its customers through its own
channels and lawful basis.

## 7. Privacy & GDPR (UK)

This integration handles the gym's customer PII. Non-negotiables:

- **Roles.** The gym is the **data controller** of RGP data; BetaLog is a
  **data processor** acting on its instructions. A signed **Data Processing
  Agreement** is required before the first API call against real data — even
  (especially) with a friendly pilot gym. Template DPA is a pilot deliverable.
- **Minimisation.** Sync only what the features need: customer id, email hash,
  check-in timestamps, membership type. **Never** payment details, addresses,
  DOB, waiver contents, or emergency contacts — the API may expose them; we
  don't store them.
- **Unlinked members.** Member docs for people who never install BetaLog hold
  the minimum (hashed email, visit counters) and exist to power *the gym's own*
  staff dashboard — processing under the gym's legitimate interest as
  controller. Configurable retention (default: purge unlinked member docs
  after 12 months of inactivity).
- **Linked members.** Linking is explicit consent, recorded with a consent
  version; unlinking in Settings deletes the join and stops any gym visibility
  of the member's app data. What the gym can see of a linked member's BetaLog
  data follows the existing privacy spec's aggregate-only principle.
- **Erasure.** RGP deletion requests handled by the gym must propagate: the
  Worker re-checks synced customers' existence periodically, and the gym gets a
  "purge member" button in the staff view. BetaLog account deletion already
  exists; it must also clear `gymLinks` and `linkedUid`.
- **UK data residency.** Firestore is already `europe-west2` (London). Keep the
  Worker's data at rest in Firestore only; the Worker itself holds nothing.

`betalog_privacy_spec.md` needs a section covering the processor role and the
linking consent screen before the pilot goes live with real member data.

## 8. Phased Delivery

Sequenced so each phase is independently valuable and the API-dependent work
starts only after the free wins are banked.

### Phase A — No API required (build now)

The highest-retention-per-effort items need zero RGP access:

1. **`session.location` / centre stamping** — already planned; prerequisite for
   everything. Ship first.
2. **Gym invite link + QR onboarding** — `betalog.co.uk/join/{gymId}` sets home
   centre, shows gym branding, lands the new user in a guided first-log flow.
   Front desk hands out the QR. This alone tests the gym's appetite and fixes
   the 53% onboarding bounce with a purpose-built landing.
3. **First-5-visits journey card** (visits = logged sessions at the centre for
   now; upgraded to true check-ins in Phase B).
4. **Manual challenge + reward** — one hardcoded programme, codes validated by
   eyeball. Proves the redemption flow with staff before any engine is built.

### Phase B — Read-only sync (the RGP integration proper)

1. Cloudflare Worker + secrets + Firestore service-account writes.
2. Check-in polling with watermarks; `gyms/{gymId}/members/*` docs; facility→centre map.
3. Member linking flow (consent screen, email-hash match, code fallback).
4. Check-in-aware app: "checked in today — log your session?", true visit
   streaks, first-visit journey driven by real visits.
5. Staff view v1: at-risk list, first-timer conversion report.
6. DPA signed, privacy spec updated, retention purge job.

### Phase C — Rewards engine + revenue features

1. RewardProgramme/RewardGrant engine + staff redemption screen.
2. Plateau detection → coaching cards; PAYG→membership prompt.
3. Bookings sync for coaching-ROI reporting.
4. Monthly gym report (retention delta, redemptions, coaching conversions).

### Phase D — Compounding with the route board

Once the route board (vision doc Phases 2–5) is live at the same centre,
everything sharpens: rewards tied to circuits and resets, coach upsell tied to
style gaps on real routes, "fresh set" notifications timed against quiet hours
from check-in data. The two workstreams multiply; neither blocks the other.

## 9. Open Questions for the Gym Conversation

1. **Hosting:** is their RGP **Cloud** or **locally hosted**? (Both support API
   keys; locally hosted needs their server reachable — affects setup effort.)
2. **Facility codes:** one per centre? Confirms the centre mapping.
3. **Data quality:** what share of walk-ins have a real email in RGP? (Linking
   rate depends on it.)
4. **Existing CRM/marketing:** what do they use for email (RGP's own tools,
   Mailchimp via Zapier, nothing)? Determines who sends win-backs.
5. **Rewards budget:** which 2–3 programmes, what's each redemption worth to
   them, who pre-creates the promo items in RGP POS?
6. **Coaching capacity:** do they have coaches with open inventory to sell, and
   how are coaching sessions booked today (RGP bookings? paper?)?
7. **Front desk reality:** will staff actually hand out QR cards and validate
   codes? (If the desk won't play, Phase A tells you before any API work is spent.)
8. **DPA appetite:** who signs data agreements — owner or a manager?
