# Session A — AI coach token cost

## AI coach — cutting the token cost per request

Ben hit Groq's rate limit on the Coach page and asked whether his own training data
was the cause:

```
Rate limit reached ... on tokens per minute (TPM): Limit 8000, Used 6796,
Requested 2481. Please try again in 9.577499999s.
```

**It was not the data.** Groq's pre-flight check bills the prompt *plus whatever
completion you reserve via `max_tokens`*, and `callGroq` hardcoded 1400 for every
call. Of that 2481-token request, ~1400 was the reservation, ~540 was fixed prompt
scaffolding (persona, JSON schema, TERMINOLOGY) and only ~540 was actual session
data. At ~2500 a call against an 8000/min ceiling you get **three requests a minute**,
full stop — "Used 6796" just means three had already gone out in the previous sixty
seconds.

### The actual waste: the dashboard tip

`CoachTip` called the same `callGroq`, so a one-sentence, twenty-word tip shipped the
entire fourteen-day per-session context *and* reserved 1400 output tokens. Measured on
a heavy 30-day log: **2706 tokens to produce one sentence.** Now 903.

### Files changed

| File | Change |
|---|---|
| `src/lib/coach.js` | **New.** Personas, context builder, `callGroq`, parsers — moved out of `pages/Coach.jsx` |
| `src/lib/goals.js` | **New.** `getCurrentValue` / `calcGoalProgress` moved out of `hooks/useGoals.js` |
| `src/lib/__tests__/coach.test.js` | **New.** 32 tests |
| `src/pages/Coach.jsx` | Imports from `lib/coach`; 539 → 300 lines |
| `src/components/dashboard/CoachTip.jsx` | Summary context, 400-token budget, date-only cache |
| `src/hooks/useGoals.js` | Re-exports the two helpers from `lib/goals` |

`lib/coach.js` needed the goal-progress maths, but `useGoals.js` imports `useData`
from `App.jsx` — importing it from `lib/` would have pulled the whole DataContext
into the graph. Hence `lib/goals.js`. The hook re-exports both names so
`GoalsSection.jsx` is untouched. Note the re-export has to be
`import` + `export {}`, not `export ... from` — the hook body calls
`getCurrentValue` itself, and a bare re-export does not bind the name locally.

### Four changes

**1. `max_tokens` is now per-call.** `ANALYSIS_MAX_TOKENS` 1400, `TIP_MAX_TOKENS` 400.
Not lower than 400: gpt-oss is a reasoning model and its reasoning tokens come out of
the same budget, so a tight cap gets you a well-formed *empty* response. `callGroq`
now throws a named error on empty content rather than rendering a blank card.

**2. Summary context.** `buildContext(..., { detail: 'summary' })` keeps the aggregate
lines, the three most recent sessions and the goals, and drops the per-session blocks.
1006 → 203 tokens on the same heavy log.

**3. Rate limits are translated.** `parseRetryAfter` pulls the wait out of Groq's
message (handles `9.5774s` and `1m20s`); `coachErrorMessage` turns it into
"Geoff is out of breath. The free AI tier allows about three requests a minute. Try
again in 10s." instead of a wall of org ids. Returns a self-contained sentence — the
tip card used to prefix "Coach unavailable — " and two em dashes read as a stutter.

**4. Notes are capped** at 200 chars (`NOTE_MAX`), whitespace collapsed. Session notes
are unbounded free text and were going into the prompt whole — the one realistic way
for a user's own data to blow the limit on its own.

Also: the tip cache is keyed on the **date alone**, not date+persona. Trying all four
personas on the Coach page used to cost four more tip calls. The cached tip now
renders under the persona that *wrote* it, since the voice is baked into the sentence.

### Net effect

| Request | Before | After |
|---|---|---|
| Dashboard tip | ~2706 | **903** |
| Full analysis | ~2946 | unchanged |
| Persona switch ×4 | 4 extra tip calls | **0** |

The analysis itself is deliberately untouched — it is the one call that genuinely
wants the detail and the output budget.

`npm test` 366 passing (32 new) · `npm run lint` 0 errors · `npm run build` clean.

Ran against a stubbed Groq endpoint in Chromium with a 20-session log: the tip fires

## Flaky gate found while merging

Merging to `main` and re-running the suite turned up a failure that had not appeared
on the branch:

```
FAIL src/lib/__tests__/weightGoalScore.test.js > keeps the scan bounded on a long daily log
AssertionError: expected 134 to be less than 120
```

Measured properly: **0/25 runs failed on `af2ea03`, 2/25 on the merged tree** — about
one in twelve. The cause is not the coach change. `demonstratedLossRate` asserted a
fixed wall-clock budget of 120ms, and the real figure on this machine is ~75ms. That
1.5x margin was thin enough that adding a thirteenth file to the parallel suite —
`coach.test.js` — was on its own enough to tip it over.

Fixed by measuring against the unbounded call instead of the clock:

```js
const bounded   = elapsed(() => demonstratedLossRate(log))
const unbounded = elapsed(() => demonstratedLossRate(log, 28, null))
expect(bounded * 3).toBeLessThan(unbounded)
```

Bounded ~75ms, unbounded ~540ms, so the ratio is ~7x and a 3x gate still catches the
regression the test exists for — an unbounded scan over a three-year daily log — while
calibrating itself to whatever the machine is doing at the time. **0/30 runs failed
after the change.** The test was not skipped or weakened in intent; it now measures
the thing it was always about.

## Shameometer — scoring the schedule you ignored

Ben's ask: flag missed scheduled routines, with a gauge "from great to bad".

Every existing widget summarises what *was* logged, so a routine could sit in the
schedule firing reminders for weeks and never surface anywhere as a failure. His own
data is the case for it: three schedule entries, 37 due days in the last 30, zero
done.

**New files:** `src/lib/adherence.js`, `src/lib/__tests__/adherence.test.js` (26
tests), `src/components/dashboard/ShameometerCard.jsx`.
**Touched:** `Dashboard.jsx` (import, `DEFAULT_ORDER`, render case), `WidgetPicker.jsx`
(option + cap), `widgetWindow.js` (chips + default), `widgetCollapse.js` (comment only).

### The three scoring rules

These are the whole feature; the arithmetic is trivial beside them.

1. **Today is never missed.** The window ends *yesterday*. A routine due today is
   still in play, and counting it would drag every score down each morning and
   recover it each evening — noise, not signal.
2. **Nothing before `remindFrom` counts.** That field already holds the first
   scheduled day at the time the reminder was set, so it is the honest start of the
   commitment. Without it, adding a routine today opens with weeks of retroactive
   failure for days when nothing was promised.
3. **Default routines match by family, not by versioned id.** Seeded routines carry
   a version suffix and a session stores whichever id was current when it was logged.
   Ben's schedule points at `dr-submaxrepeaters-v5` while all three of his hangboard
   sessions are `dr-submaxrepeaters-v4` — a strict id match scores real sessions as
   zero and reports "never done". `routineFamily()` strips a trailing `-vN`, and only
   from `dr-` ids so user uuids are untouched.

Also: the overall percentage **pools due days** rather than averaging the per-routine
rates. A routine scheduled 7×/week is a bigger commitment than a Monday one, and
averaging lets the Monday one paper over it — on Ben's data pooling gives 0% where
averaging would flatter it.

`scored: false` when nothing was due in the window (new schedule, or one whose
weekday hasn't come round), so the card says so instead of showing a 0% nobody
earned. The card renders nothing at all when the schedule is empty.

### The gauge

`SHAME_BANDS`, eight rungs, best first: Flawless 95 · Locked in 85 · Solid 70 ·
Wobbly 55 · Patchy 40 · Shaky 20 · Ghosting it 1 · Total shame 0. Deliberately
uneven — the top is split finely because the difference between 90% and 100% is
where the habit lives, while everything under 40% is the same message told louder.
Tone is the only thing in the array, so retuning it is a one-file edit.

Body is a tinted meter bar, the band's note, a per-routine breakdown sorted
worst-first, and a "Worst: X · N in a row missed · last done Y" line. A percentage
alone is arguable; a date is not.

### Config

- Windows `30d` / `90d`, defaulting to **30d** — this is an "are you doing it *now*"
  card and a quarter lets a good month hide a bad fortnight. No `12m`: `remindFrom`
  truncates the window anyway, and on Ben's data 30d and 90d already return the
  identical 0/37.
- Not in `COLLAPSE_DEFAULTS`, so it arrives expanded. It has no chart, and a card
  whose job is to be uncomfortable does not get to arrive pre-folded.
- `MAX_WIDGETS` 10 → 12. Ten options against a cap of ten would render every chip
  as at-limit the moment they were all on.

## Weekly Shameometer — built

Ben approved the defaults but pushed back on one thing: *"for scheduled routines
missed seems a big penalty perhaps?"* He was right that something was unfair, but it
turned out not to be the weight.

**Tested the weight first.** The cost of ignoring the schedule is exactly `W_SCHED`,
on every week — 25 points at weight 25, 15 at weight 15. On a typical week (6 pts,
18 units) that is POOR→GOOD across the range at 25, but at 15 the range collapses:
POOR whether every routine was done or none. Dropping the weight makes the routines
feel pointless, which is a worse failure than being harsh. **Kept at 25.**

**The real unfairness was the denominator.** Ben's schedule asks for 17 routine
sessions a week — prehab M/W/F plus *two* routines scheduled daily. Prehab three
times, a genuinely good week, banked 3/17 = 18%. So the component was unwinnable in
practice. Changed to score **per scheduled day**, not per routine instance: a day is
due when anything is scheduled on it, done when any routine due that day was logged.
Prehab ×3 becomes 3/7 = 43%. Identical at the extremes, fairer in the middle.

**Also flagged to Ben, and more important than the scoring:** Sub-Max Repeaters is
scheduled *seven days a week* with two reminders a day. Nobody should hangboard
daily. The app was nudging him toward an injury and the score would then have shamed
him for declining.

### Found while verifying: EXCELLENT was unreachable-proof at the top

The first render read **85 · EXCELLENT** on Ben's real week with the schedule at
0/25. Perfect training (75) plus the dry bonus (10) is exactly 85 — so an EXCELLENT
threshold of 85 meant the schedule could *never* change the verdict at the top of the
scale, which is most of the reason it exists. **Raised EXCELLENT to 88.** His week now
reads GOOD, and honouring the scheduled days takes it to 100. Two tests guard that
boundary by name.

**Rewritten:** `ShameometerCard.jsx`.

### The dial

Inline SVG, no library. 180° arc, five segments drawn as annulus sectors from polar
points, needle as a polygon on an exact pivot. Band labels are **not** on the arc —
five labels round a semicircle either collide at the ends or need tangential
rotation, both of which read badly at 400px. They sit in a legend row underneath,
where the active band can also be highlighted, which the arc could not do. Inactive
segments drop to 0.28 opacity so the band you are in is the one that reads.

Body: the dial, the band's line, a seven-day strip of points per day, the three-row
component breakdown, per-routine "last done", and a "biggest gain" line naming the
single largest swing available.

### One consequence worth knowing

Because the needle reads *on pace*, it drifts down on any day nothing is logged and
jumps up when something is. A week that starts strong and stops will fall back. That
is intended — it makes the dial a live nudge rather than a Sunday verdict — but the
mid-week number is not a prediction of where the week will finish.

## Sealed week log

Ben: *"can we log each week (Sunday night) the shame score for that week."*

**There is no Sunday night.** A PWA cannot wake itself at 23:59 — `setTimeout`
only fires while the tab is open, the push Worker holds no session data, and
Cloudflare Pages has no per-user cron. So a week is sealed on the **first app open
after it ends**, with backfill for anything missed. Monday morning or three weeks
later produces identical records.

**Stored, not derived** — the important decision. The score is computable from data
already kept, but every input is mutable: editing the schedule (which Ben is about
to do, pruning Sub-Max Repeaters off daily) would shrink the denominator for every
past week and silently improve the whole history. A sealed record says what he
actually got. `scoreVersion` marks the ruleset, so a later retune is visible.

`sealWeeks` is idempotent — a recorded week is never rescored. A test asserts
exactly the schedule-pruning case.

Empty weeks are skipped: no sessions, no drinks, nothing scheduled means the app
wasn't in use, and logging "10 — nothing done, nothing drunk" would fill the
history with noise that looks like data.

**Files:** new `src/lib/weekLog.js`, `src/lib/__tests__/weekLog.test.js` (19 tests),
`src/hooks/useWeekScores.js`. Touched `storage.js` (`il_weekScores` key + SYNC_KEYS
+ merge), `types.js` (WeekScore typedef), `Dashboard.jsx`, `ShameometerCard.jsx`
(history strip).

The Firestore merge for this key **unions by week rather than replacing**, unlike
every other key — a sealed week is a record of what happened, so whichever device
wrote it first wins and nothing is lost when two devices sealed different weeks
offline.

### Verified against real data

Backfilled **25 weeks** from Ben's export on first open, persisted to localStorage,
and added nothing on a second open (records byte-identical). Last completed week
correctly flagged `backfilled: false`, the 24 older ones `true`.

### Known limitation this surfaced

w/c 13 April sealed at **100 EXCELLENT** — five consecutive days of *ankle rehab
physio*. A `gym` session scores 2 whatever it contains, so ankle alphabet counts
like an hour of lifting. Two honest readings: during injury, doing physio five days
running genuinely is an excellent week; against that, it makes early history not
comparable with later. `difficulty` would not fix it (those were logged as 2, same
as everything else) — it needs session content. Flagged in the spec, not changed.

Widgets that pass no `preview` behave exactly as before.

### What the preview shows

One row, two strips:

| Strip | What it is |
|---|---|
| Score bars | Up to 10 sealed weeks + **this week as an outline bar** · `10 sealed wks · avg 44` |

The live week is hollow rather than filled because a solid bar would claim a
