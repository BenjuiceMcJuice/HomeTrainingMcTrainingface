## Hangboard timer keeps the screen awake

**Merged 2026-09-17 on Ben's word — *"Just push to prod."* Not seen on a phone first; the check below still applies to the live site.**

- **`src/hooks/useWakeLock.js`** — one hook, `useWakeLock(active)`. Requests
  `navigator.wakeLock.request('screen')` while `active` is true, releases it on false or unmount.
  iOS drops the lock every time the app leaves the foreground, so it listens for
  `visibilitychange` and asks again on return. Missing API (iOS before 16.4, Firefox) and a
  refusal (Low Power Mode) are both silent — the timer works as before, the screen just follows
  auto-lock.
- **`HangboardTimer.jsx`** — holds the lock whenever the sheet is open and the phase is not
  `preview` or `done`. Paused counts as running: the climber is still on the board.
- Nothing else is timed. The only other `setInterval` is the Coach page's rate-limit countdown.
- Cache v29 → v30.

**651 tests, 0 lint errors, build clean.** Not verified on a phone — the timer is behind
sign-in and the lock only means anything on a real screen. Check on the preview deploy: start a
routine, put the phone down for longer than Auto-Lock, and the display should still be on.

## The beep lands on the number

Ben, on the board with Bluetooth headphones: *"the 'beep' happens just after the number changes.
Not as it changes."* It did, by design of the old code: the 200 ms poll flipped the number,
React painted it, and only then did a `useEffect` notice and call the tone — plus whatever the
audio path adds, which on Bluetooth is 150–250 ms. The eye got the number, the ear got the beep
a fifth of a second later.

**Branch `claude/iphone-screen-lock-pwa-4cvum5`, not merged.** New feature; waiting on the word.

- **`src/lib/hangTimer.js`** — the state machine moved out of the component (unchanged), plus
  the cue schedule: `cueAtBoundary(ts, k, grips)` says what sounds `k` seconds into a phase run
  (silent, then `lastSeconds` / `countdownTick` for the last three, then the *next* phase's
  start cue at zero); `dueBoundaries` lists the boundaries inside a horizon not yet booked;
  `leadSeconds` is the reported latency (`baseLatency + outputLatency`) plus the user offset,
  clamped 0–500 ms. All pure, 12 tests.
- **`HangboardTimer.jsx`** — the tick now does two things off one wall-clock anchor. A one-shot
  timeout aimed at the next second boundary flips the number *on* it (the 100 ms poll is the
  safety net for a throttled tab). And every 100 ms it books any boundary within 300 ms + lead:
  the cue is scheduled on the audio clock at boundary − lead, so it reaches the ear as the
  number changes. `playTone` takes a start time and returns a handle; a cue booked for a second
  the run never reached (Skip, Pause, close) is silenced by disconnecting its output. A phase
  the clock reached has its cue booked ahead, so the phase-change effect only plays for phases
  the climber started by hand (Start, Skip, End) — a ref says which.
- **Settings › Beep timing** — a stepper in ms with *Speaker* (0) and *Bluetooth* (180)
  presets, device-local in `il_audioOffsetMs` like the Groq key, since headphones belong to a
  phone. The row also shows what the phone reported last session (`il_audioLatencyMs`),
  which is the thing to read: if iOS reports the Bluetooth delay itself the preset
  double-counts and should come down.
- Cache v30 → v31.

**Verified in headless Chromium** through a harness that mounts the timer with a stubbed data
context and instruments the audio graph. With a 180 ms offset every booked tone started
224 ms before its number flipped — the 42 ms Chromium reports plus 180, to within 2 ms —
and the numbers flipped within 3 ms of each second. Start and Skip cues played immediately,
phase-change cues once. Skip and Pause each cancelled the one tick booked for the second they
cut off; Resume re-booked from the frozen count. **663 tests (12 new), 0 lint errors, build
clean.** Not heard on a phone: what iOS reports, and whether 180 is the right preset for
AirPods, is the thing to check on the preview.
