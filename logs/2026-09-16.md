## Is the pyramid base accurate? — measuring the model instead of arguing about it

Ben: *"Is the pyramid base thing accurate ie if you've done two V4s your ready for v5???"*

Answered by running `lib/pyramid.js` against made-up logs rather than reading the spec back at him.
No behaviour changed; three documentation claims did, and two new backlog rows opened.

### The answer

**No — two V4s reads `No base yet`, 1/5.** Target V5 walks `1·2·4·8` down from V5: the V4 row is met
at 2/2, V3 is 0/4 and V2 is 0/8, and readiness is the weakest row, so it floors at 1. Exactly what
§4.3 rule 2 specifies.

### What the measurement turned up next door

Spill has been carrying the model alone since the per-session cap was removed (BTL-B30), and it
reaches further than the 1·2·4·8 shape implies:

```
14 V4s, ONE session, nothing else   ->  Base complete (5/5)  V5 0/1  V4 2/2  V3 4/4  V2 8/8   ready = V5
20 V4s + 2 V5s, no V6 attempted     ->  Base complete (5/5)                                    ready = V6
14 V4s from late March, none since  ->  Base complete (5/5)
8 sends of the same V4              ->  Base thin (2/5)
```

The first two are one evening and one grade respectively building a whole base. Filed as **BTL-B39**
(a decision for Ben, not a defect — it follows directly from decisions 1 and 7, and errs flattering)
and **BTL-B40** (the window is undated inside itself; correct by the spec's reasoning, worth saying
out loud in the explainer).

Checked and found **sound**: `describeNextUp` names one row at a time but each is a genuine
prerequisite — follow it twice from two V4s (8 V2s, then 4 V3s) and the base does complete.
Attempts never leak into `credited`: 30 unsent V3s still read 0/4.

### The drift

`MAX_SENDS_PER_SESSION` went to `Infinity` on 2026-09-13. Three places still said it was 2:

- `lib/pyramid.js` module note, rule 2 — *"One session cannot fill a tier"*, flatly false, and the

- `BACKLOG.md` — BTL-B30 sat under **Open** in present tense while the closed table said it shipped

One fact in three places, all three wrong, which is the failure the backlog standard was written
after. Section retitled BTL-B9, BTL-B30 marked closed where it stood.

## The same question with a real card on it — BTL-B41, BTL-B42

Ben, later: screenshot of the Dashboard boulder card — `Base V2 · Best V3 · Flash V3`, goal **send
V5**, 137d left, `V2 8/8 · V3 3/4 · V4 0/2 · V5 0/1`, "No base yet", 3 sessions in 180 days, *"Ready
for V5 around mid-January at your current rate. That is 2 weeks inside your deadline."*

*"Today i did some V3s and the bar is nearly full. This pyramid suggests that when I've done 2 V4s
I'll be ready for V5…. Discuss?"*

Rebuilt his log against the model and reproduced the card (the 2-V4 case lands on his exact
"mid-January … 2 weeks inside your deadline").

```
as it is today     V5 0/1  V4 0/2  V3 3/4  V2 8/8  -> No base yet (1/5)       nextUp: Log 2 more V4s
+ 2 V4s            V5 0/1  V4 2/2  V3 3/4  V2 8/8  -> Base nearly there (4/5) nextUp: Log 1 more V3
+ 2 V4s and a V3   V5 0/1  V4 2/2  V3 4/4  V2 8/8  -> Base complete (5/5)
```

**His reading is right, and the shape is not at fault** — 1·2·4·8 down from V5 is Hörst's pyramid,
and V4's row can only be filled by real V4 sends because spill runs downward. What is at fault is
the two sentences underneath, both flattering:

**BTL-B41** — `fillRate` measures from the first climb *in the window* to today, so a four-month gap
at the **start** is free while the same gap at the **end** is charged. Same 3 sessions, same 11
sends: clustered recently → 5.77/month, late January, 4/5; spread evenly → 1.91/month, early March,
3/5. The card prints *"3 sessions in 180 days"* directly above a rate implying one session a
fortnight.

**BTL-B42** — the shortfall is divided by one rate pooled across all base grades. His 5.77/month is
earned on V2s; the 3 sends he needs are two **V4s** (never touched) and a V3. So the card says
*"Base full in about 2 weeks"* — two weeks to send two V4s, from a log whose best ever is V3. The
per-grade rate that would fix it already exists from BTL-B33, applied to an *Own* goal's target row
and never to the base shortfall.

Checked and **sound**, recorded so it is not relitigated: `Base complete` never asserts the target
was sent, and 17 weeks of conversion time is still charged after the base fills. The model does not
say "2 V4s and you have V5".

No code changed — both are Ben's call, as they move every grade goal's forecast.
