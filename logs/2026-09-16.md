# 2026-09-16

## Is the pyramid base accurate? — measuring the model instead of arguing about it

Ben: *"Is the pyramid base thing accurate ie if you've done two V4s your ready for v5???"*

Answered by running `lib/pyramid.js` against made-up logs rather than reading the spec back at him.
No behaviour changed; three documentation claims did, and two new backlog rows opened.

### The answer

**No — two V4s reads `No base yet`, 1/5.** Target V5 walks `1·2·4·8` down from V5: the V4 row is met
at 2/2, V3 is 0/4 and V2 is 0/8, and readiness is the weakest row, so it floors at 1. Exactly what
§4.3 rule 2 specifies.

### What the measurement turned up next door

Spill has been carrying the model alone since the per-session cap was removed (BTL-B30), and it
reaches further than the 1·2·4·8 shape implies:

```
14 V4s, ONE session, nothing else   ->  Base complete (5/5)  V5 0/1  V4 2/2  V3 4/4  V2 8/8   ready = V5
20 V4s + 2 V5s, no V6 attempted     ->  Base complete (5/5)                                    ready = V6
14 V4s from late March, none since  ->  Base complete (5/5)
8 sends of the same V4              ->  Base thin (2/5)
```

The first two are one evening and one grade respectively building a whole base. Filed as **BTL-B39**
(a decision for Ben, not a defect — it follows directly from decisions 1 and 7, and errs flattering)
and **BTL-B40** (the window is undated inside itself; correct by the spec's reasoning, worth saying
out loud in the explainer).

Checked and found **sound**: `describeNextUp` names one row at a time but each is a genuine
prerequisite — follow it twice from two V4s (8 V2s, then 4 V3s) and the base does complete.
Attempts never leak into `credited`: 30 unsent V3s still read 0/4.
