## The docs had drifted

Five specs still described work that has shipped, and one privacy statement had become untrue.
Nothing in the code changed today; all of it is documentation correction.

**1. The privacy spec said BetaLog uses no analytics. It does.** This was the open follow-up
recorded in `DEVLOG.md` when the Cloudflare Web Analytics beacon went in — never actioned. The
legal section read:

> No other third-party services receive your personal data. BetaLog does not use advertising
> networks, analytics platforms, or tracking pixels.

`betalog-react/index.html` has served `static.cloudflareinsights.com/beacon.min.js` to every
visitor since that work. The sentence was accurate when written and false by the time it mattered.

Corrected in both halves of the document, because the spec carries the page's draft copy as well
as its build plan:

- **Third-party table** — Cloudflare Web Analytics added as a row, alongside Firebase and Groq,
  naming what it receives (page URL, referrer, browser, country) and what it does not (cookies,
  identifiers).
- **The blanket sentence** narrowed to advertising networks and *cross-site* tracking pixels, which
  remains true, followed by a paragraph on why the cookieless distinction matters: no cookies,
  nothing stored on the device, no identifier that survives a visit, so no PECR consent banner and
  nothing to opt out of. Legal basis stated as legitimate interests, matching the other entries.
- **Plain-English "What we don't do"** — the same fact in the register the rest of that section
  uses. "We do count page views" leads, because a reader who finds the omission themselves will
  not trust the rest of the list.

Worth being precise about the scope of this: **the privacy page does not exist.** There is no
`/privacy` route and no HTML file — `find` turns up the spec and nothing else. So the wrong text
was never served to anyone; it was wrong in the document that will become the page. Fixing it now
means the inaccuracy cannot be built in later, which is exactly the failure mode the DEVLOG note
was warning about. `CLAUDE.md`'s index row now says the page is unbuilt, so the next session does
not have to rediscover it.

## Route B — web push, built

Ben's verdict on the calendar reminders was "works but it's rough", then asked for the slicker way
on a branch. That is Route B in `docs/specs/betalog_reminders_spec.md`, deferred on 19 August
pending exactly this judgement.

**Route A is kept, not replaced.** They are independent — either, both or neither can be on. Push is
better where it works; the calendar feed is the one that works everywhere.

### What was rough, and which of it this actually fixes

| Route A problem | Route B |
|---|---|
| Tapping the alert opens Calendar, not BetaLog | Opens the app, deep-linked to `/log?routine=<id>` |
| iOS **Remove Alerts** strips every VALARM unless turned off by hand | No equivalent — nothing to configure |
| Subscribed calendars refresh on the phone's schedule; can be hours | Sent when the cron fires; worst case 5 min |
| Can't know whether you already logged that session | The Worker could check — not built, but now possible |

### The pieces

- `src/lib/pushSchedule.js` — the due-time rule, pure and tested. **The Worker imports this file
  directly** rather than reimplementing it, which is the precedent the calendar Worker set by
  leaving the whole `.ics` builder in the app. Verified the import genuinely resolves by grepping
  the bundled output for the notification copy.
- `src/lib/push.js` — support detection, tokens, base64url, subscription serialisation, mirror
  client. `pushSupport` takes its readings as an argument rather than reading globals, so the iOS
  states can be tested on hardware nobody here owns.
- `usePush.js` + `PushSync.jsx` — modelled on `useCalendarFeed`/`CalendarFeedSync`, including the
  module-level in-flight guard that stops two mounted copies racing into duplicate PUTs.
- `PushReminders.jsx` in Plan → Schedule, above the calendar card.
- `public/sw.js` — `push` + `notificationclick`. **`CACHE_NAME` bumped v2 → v3.** Without it an
  existing install keeps the old worker and never receives the handlers — the same trap the
  analytics beacon nearly fell into.
- `workers/betalog-push/` — `PUT`/`DELETE /sub/<token>`, KV-backed, `*/5` cron sender.

### Decisions taken while building

**A subscription is per device, so `il_pushSub` is deliberately left out of Firestore sync.** This is
the opposite of the calendar feed, and worth stating because the two look alike. A feed is one URL
per user, meant to be shared between devices. A push endpoint is issued by one browser on one
device — syncing it would put the phone's endpoint on the laptop, where turning notifications off in
one place silently breaks the other.

**A 60-minute grace window.** A reminder fires on the first tick at or after its time, and is dropped
if it is more than an hour late. Without it, a Worker that was down all morning comes back and fires
every missed reminder at once — telling you to train at 07:00 when it is 11:00 is worse than
silence.

**Dedupe per entry per local day**, marked immediately after a successful send. A duplicate reminder
is a worse bug than a missed one, and the grace window already bounds the retry.

**No `GET` on the Worker.** Nothing needs to read the mirror back, and one that could be fetched with
the token would turn a leaked URL into a push endpoint a stranger could send to.

**The title drops the " — BetaLog" suffix** that the `.ics` uses, because iOS already prints the app
name above it. Keeping it would read "Glutes!!! — BetaLog / BetaLog".

### A correction I had to make mid-conversation

I told Ben that snooze/done buttons on the notification were a Route B win, taking it from the
spec's open-questions list. That list describes the Push API in general; **whether iOS honours
`actions` in an installed web app is unverified**, and I shouldn't have implied he'd get them.
Nothing built depends on it — the tap target is the notification itself. Flagged in the spec so the
assumption doesn't get inherited.

### Verified

- **246 unit tests** (was 190), build green, lint 0 errors and no new warnings.
- **18 Worker smoke checks** (`workers/betalog-push/scripts/smoke-test.mjs`) against an in-memory KV
  and a stubbed push service: sends when due, marks the local date, doesn't resend the same day,
  ignores wrong days and future times, prunes a 410, retries a 500 without marking, respects the
  entry's own timezone, sends two due entries separately, skips a malformed record without killing
  the tick.
- **The smoke test's first run failed usefully.** All eight send assertions failed because I'd
  fabricated a `p256dh` that isn't a real point on the P-256 curve — `buildPushPayload` does an
  actual ECDH, so it threw, and my `catch` counted it as a transient failure. Worth knowing: a bad
  subscription key looks exactly like a network wobble from inside the Worker. Fixed by generating
  a genuine keypair for the test.
- **`wrangler deploy --dry-run` bundles cleanly** at 18.56 KiB, proving both the cross-directory
  import and that the push library builds for Workers.
- **The card driven in Chromium at 400px** across all five states: supported-and-off, enabled with
  two timed routines, enabled with none, iOS-Safari-tab (Push APIs stripped, iPhone UA) showing the
  install advice, and a browser with no support at all rendering nothing. Confirmed the two-tap
  confirm on the off switch. The app itself needs Firebase sign-in, which is unreachable from this
  sandbox, so the card was mounted against a stub context — a throwaway harness, deleted after.

### What is NOT verified

**No notification has been delivered to a real device.** That needs the VAPID keys, the KV
namespace, a deploy and a phone — none of which exist yet. Everything above tests the decisions
around the send, not the arrival. The three device unknowns from the earlier conversation also
stand: whether action buttons exist at all, whether `navigator.setAppBadge` works, and how the
notification icon renders given `manifest.json` declares a single SVG.
