# 2026-09-03

First session since 2026-08-21. Opened with "what's next" — so the work was to establish what
*is* next, and the answer turned out to start with the docs being wrong about the app.

## The docs had drifted

Five specs still described work that has shipped, and one privacy statement had become untrue.
Nothing in the code changed today; all of it is documentation correction.

**1. The privacy spec said BetaLog uses no analytics. It does.** This was the open follow-up
recorded in `DEVLOG.md` when the Cloudflare Web Analytics beacon went in — never actioned. The
legal section read:

> No other third-party services receive your personal data. BetaLog does not use advertising
> networks, analytics platforms, or tracking pixels.

`betalog-react/index.html` has served `static.cloudflareinsights.com/beacon.min.js` to every
visitor since that work. The sentence was accurate when written and false by the time it mattered.

Corrected in both halves of the document, because the spec carries the page's draft copy as well
as its build plan:

- **Third-party table** — Cloudflare Web Analytics added as a row, alongside Firebase and Groq,
  naming what it receives (page URL, referrer, browser, country) and what it does not (cookies,
  identifiers).
- **The blanket sentence** narrowed to advertising networks and *cross-site* tracking pixels, which
  remains true, followed by a paragraph on why the cookieless distinction matters: no cookies,
  nothing stored on the device, no identifier that survives a visit, so no PECR consent banner and
  nothing to opt out of. Legal basis stated as legitimate interests, matching the other entries.
- **Plain-English "What we don't do"** — the same fact in the register the rest of that section
  uses. "We do count page views" leads, because a reader who finds the omission themselves will
  not trust the rest of the list.

Worth being precise about the scope of this: **the privacy page does not exist.** There is no
`/privacy` route and no HTML file — `find` turns up the spec and nothing else. So the wrong text
was never served to anyone; it was wrong in the document that will become the page. Fixing it now
means the inaccuracy cannot be built in later, which is exactly the failure mode the DEVLOG note
was warning about. `CLAUDE.md`'s index row now says the page is unbuilt, so the next session does
not have to rediscover it.

**2. Four specs said "Planned" or "not started" for features that are live.** Each verified
against the code before the header was touched, not assumed:

| Spec | Said | Actually |
|---|---|---|
| `betalog_ia_declutter_spec.md` | planned, not started | all four phases shipped 2026-08-20 |
| `betalog_goals_spec.md` | Planned | `GoalsSection.jsx`, `Storage.saveGoals`, `Goal` in `types.js` |
| `betalog_health_log_spec.md` | Planned | `HealthMode` in `Log.jsx`, `useDrinkLog.js`, `AlcoholFreeCard.jsx` |
| `betalog-calorie-tracking-spec.md` | Specced, not yet implemented | MET tables + `estimateSessionKcalMid()` in `stats.js` |

The IA declutter one was the sharpest: `CLAUDE.md` and `DEVLOG.md` both recorded it complete while
its own header still said not started. A stale header is worse than no header — it invites someone
to build a thing twice.

The `Goal` typedef in `types.js` matches the spec's data model field for field, so that spec is an
accurate description of what exists and is kept as the design record rather than being archived.
Same for the others: each header now points at the files that implement it.

**3. `CLAUDE.md` fixes.** The file structure described `Log.jsx` as "Train/Climb/Hang modes"; the
`MODES` array has five — Cardio and Health were added and the note never followed. The
documentation index was missing six specs that exist on disk (goals, health, cardio, calorie
tracking, reminders, and the custom-cardio idea), so a new session reading the index would not
know they were there.

## What this leaves for next time

The two items that genuinely need a decision or a laptop, unchanged by today:

- **The `friendCodes` Firestore rule fix is merged but not deployed.** `firestore.rules` in `main`
  correctly narrows `allow read` to `allow get`, closing an enumeration hole. Rules do not ship
  with a Cloudflare deploy — production stays exposed until someone runs
  `cd betalog-react && firebase deploy --only firestore:rules`. Cannot be done from a cloud
  session. This is the highest-value open item and it is one command.
- **The AI coach output review** — the largest planned piece, and the one with open questions
  (does a generated mini plan persist? is drink + weight + cardio enough for a diet review to say
  anything?). Needs Ben's call before building.
