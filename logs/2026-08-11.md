## Schedule reminders: investigated and specced

Ben asked whether BetaLog could send him phone reminders for his scheduled routines. Written up in
`docs/specs/betalog_reminders_spec.md` and summarised in `DEVLOG.md`.

### What the codebase already gives us

- **PWA foundations are in place**: `public/manifest.json`, `public/sw.js`, registered in
  `src/main.jsx`. The SW is cache-only today — no push handlers.
- **Firebase Auth + Firestore** for per-user storage.
- **A Cloudflare Worker already deployed** (`benjuicey-feedback`), so the account, the deploy pattern
  and the CORS approach are all established. A second Worker is not new ground.
- **`useSchedule.js`** — up to 3 entries of `{id, routineId, routineName, days[1–7]}`.

### The gap that blocks both routes

`ScheduleEntry` records **days but no time of day, and no timezone.** A reminder needs both. Adding
optional `remindAt: "HH:MM"` and `tz` (from `Intl.DateTimeFormat().resolvedOptions().timeZone`) is
the first task whichever route is taken, and both fields being optional means existing schedules
keep working untouched.

The timezone is not optional in practice: a Worker runs in UTC, so without `tz` every reminder is an
hour out for half the year.

### Two routes, and why the order matters

**Route A — calendar feed.** Worker serves a private `.ics` at a token URL; the phone subscribes once
and its own Calendar app fires the alerts. The existing `days` array maps directly onto an `RRULE`,
so the transformation is trivial. No permission prompt, no Home Screen requirement, no iOS caveats,
and it fires whether or not the app has been opened in weeks — which is exactly when a reminder is
worth having.

**Route B — web push.** SW `push` handler, permission from a user gesture, subscription mirrored to
KV, Cloudflare Worker on a Cron Trigger sending via VAPID.

**Route A first, deliberately.** It is a fraction of the work and it answers a question Route B
cannot: does a nudge actually change what Ben does? Building the push stack first would mean
committing to a platform constraint on the assumption that reminders help.

### Things worth knowing before building Route B

- **Node's `web-push` does not run on Cloudflare Workers** — it needs Node crypto. Use a WebCrypto
  library: PushForge or `@block65/webcrypto-web-push`, both built for exactly this.
- **Don't have the Worker read Firestore.** Authenticating a Worker to Firestore is fiddly, and the
  sender only needs `{endpoint, keys, days, remindAt, tz, routineName}`. Mirror that into KV on save
  and the Worker never touches Firebase.
- **A 15-minute cron needs a dedupe key** (`lastSentDate` per entry) or one reminder fires four
  times.
- **iOS push requires Home Screen install.** The Push API is not exposed to a Safari tab and hasn't
  been since it arrived in iOS 16.4. Ben has it installed; for anyone else the feature must be
  feature-detected, opt-in and off by default, with a specific message for the
  iOS-but-not-installed case rather than a switch that silently does nothing.

### Correction recorded

An earlier note in this conversation claimed the SVG `apple-touch-icon` would leave iOS showing a
blank Home Screen icon, and treated a 180×180 PNG as a prerequisite. **Wrong** — Ben's Home Screen
renders the BL icon correctly. Modern iOS resolves it. No icon work is needed and it was never a
blocker. A PNG remains cheap insurance for older iOS versions, nothing more.

### Open questions carried into the spec

- One notification per schedule entry, or a daily digest? Three entries could mean three
  notifications on a bad Monday.
- Snooze or "mark done" from the notification? Push supports actions; a calendar alert doesn't.
- Suppress the reminder if a session is already logged that day? Straightforward for push (the
  Worker can check), impossible for a static calendar feed.
