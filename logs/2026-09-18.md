## BTL-B44 — bottom tabs floating

**Merged 2026-09-18 on Ben's word — *"Push to main."* Not seen on a phone first; the check below still applies to the live site.**

**Cause.** The mobile bottom nav is `position: fixed` with `backdrop-filter: blur(12px)`.
WebKit has a long-standing compositing bug where a fixed element carrying a backdrop blur is
painted at a stale scroll offset after the document's height changes underneath it — a widget
collapsing or expanding, a sheet closing, the keyboard dismissing. The page scrolls, the bar
does not follow, and the blur layer smears the content it used to sit over. That is exactly the
screenshot: bar mid-page, whited-out band beneath it, "V4 / V5" rows showing through the edge.

**Fix — `src/components/layout/Nav.jsx`.**
- `backdropFilter` removed from the bottom nav. Background is now solid `#ffffff` instead of
  92% white; there was almost nothing to see through it anyway.
- `transform: translateZ(0)` on the bar so it has its own compositing layer and is repositioned
  with the viewport rather than repainted with the page. A transform on the fixed element itself
  does not break its fixed positioning — only a transform on an ancestor does.
- The sticky top header and the desktop nav keep their blur — the bug is specific to `fixed`.
- Comment in the JSX says why, so nobody adds the blur back for looks.
- Cache v33 → v34 so installed phones drop the old bundle.

**668 tests, 0 lint errors, build clean.** The bug is intermittent and only reproduces on iOS, so
it is not verified on a phone. Check on the preview deploy: open the Dashboard, expand and collapse
the Boulder widget a few times mid-scroll, open and close a log sheet, and the bar should stay on
the bottom edge throughout.

Released the same day on Ben's instruction.

### Second pass — two boards, and every window said

Ben: *"It needs to be clear exactly what data we're showing. I'd like it to be to help stoke
competition between friends on what they're climbing. With the leaderboard aspect also somehow."*
Asked two questions, both answered with the recommendation: the competitive board ranks on the
hardest send then send count, over a rolling 30 days.

**Why a second board.** The existing board ranks on the level word, which is the Base over 180
days. Fair, and slow — eight sends at one grade — so nothing on it moves when a friend has a big
session. Competition needs a number that moves. A base is a claim about what is built and needs
the long window; hardest send and send count are plain counts, which the honesty spec allows at
any window it names.

**Built.**
- `lib/goals.js` — `RECENT_WINDOW_DAYS = 30`. Each level on the profile adds `recent`
  (`windowDays`, `hardestSend`, `sends`, `flashes`, `sessions`, from `buildPyramid` over 30 days)
  and `lastClimbedAt` (last session date with a climb in the discipline).
- `FriendsScreen.jsx` — **Level** and **Last 30 days** tabs under the discipline switch, with a
  sentence under them saying exactly what the board ranks on, and *How this works ↗* to the
  explainer. `rankEntries(entries, discipline, board)`: level → LEVEL_RANK, Base, then Best;
  recent → hardest send, sends, sessions; profiles without `recent` sort last, shown as *not
  shared yet*. Each row says when they last climbed, green within 7 days (`ACTIVE_DAYS`), grey
  after. The right-hand block answers only the current board's question. *–* for no level is
  now *no base yet*.
- Detail card, in window order: **Last 30 days** (hardest send · sends · flashes · sessions),
  **Last 180 days** (level, Base "the grade owned, 8 sends", Best, Flash, the pyramid, then
  *Per grade, last 180 days* bars), **All time** (hardest send). All-time no longer hides beside
  Best when they differ; it has its own labelled line.
- Tests: the 30-day counts and last-climb date, per discipline, and the empty window.
- Rendered both boards and the card server-side with four fake friends (new build, old build,
  quiet, hot) to check the order and the copy; throwaway harness removed.

### Third pass — older logs publish on first open

Ben: *"Will older data sync with this update?"* The log, yes — the profile is built from the
whole session log already on the device, so history is in the pyramid the moment it is
published. The publishing was the gap: the profile document is written only from
`syncToFirestore`, which runs after a `setData` or on a first-ever sign-in. A friend who
updated the app and then rested would keep the old document up and read as *not shared yet*
until their next logged session.

**Built.** `PUBLIC_PROFILE_VERSION = 2` in `lib/goals.js`, stamped on the profile as
`profileVersion`. `storage.js` records the version it last published in
`il_publicProfileVersion` after every sync, and `Storage.republishProfileIfStale(userId)`
publishes once when that is behind. `App.jsx` calls it on sign-in after the cloud merge, so it
reads the merged log. One extra write per device per shape change; nothing on every open, so
*Updated Nd ago* on a friend's page still means their last log, not their last app open.

### Fourth pass — the board is live while it is open

Ben: *"I wanna be sure linked friends data remains current / live."* It was not. `FriendsScreen`
is always mounted (it returns null when closed), so `useFriends` fetched every friend's profile
once at app start and every opening of the sheet reused that until the refresh button. A phone
that keeps the PWA in memory for days showed a days-old board. My own row was always current —
`myProfile` is built from local data on render — which made the staleness easy to miss.

**Built.**
- `Storage.watchFriendProfiles(uids, onChange)` — one `onSnapshot` per friend's
  `users/{uid}/public/profile`; emits the full list only once every profile has reported, so
  the board never briefly shrinks; returns an unsubscribe.
- `useFriends(userId, open)` — holds `uids` separately from `friends`. Reads the friend list on
  mount and again on every open. While open, watches the profiles; a new `uids` array (add,
  remove, refresh) re-subscribes; close drops the listeners, so nothing is watched in the
  background. `addFriend` checks `uids` for duplicates instead of the last snapshot.
- `FriendsScreen` passes `open`.

**What "live" means now.** Their phone syncs 300 ms after a log (`setDataAndSync`), which
rewrites their profile; the listener on your open sheet delivers it in about a second. Closed,
nothing is fetched; the next open reads fresh. Reads: one per friend per open plus one per
change while open — nothing against the Spark quota at this scale. `getFriendProfile` stays
for the one-shot path.
