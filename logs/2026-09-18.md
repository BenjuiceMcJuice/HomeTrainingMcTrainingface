## BTL-B54 — a friend's profile only republishes on the launch after next

Ben, with a screenshot of Dave's card reading *Not shared yet — their app needs to sync on the
latest version* on both boards, under a profile *Updated today*: *"How can this sync? It doesn't
seem to happen automatically."* Then: *"I want it automatic. Please."*

**Traced.** The republish from the third pass works, and it is not what was missing. Dave's
profile was written today from a bundle older than today's releases: it has base, best, flash
and level (the 13 September shape) and none of today's keys. The gap was the service worker.
It is cache-first and precaches `index.html`, so the first launch after a release served the
old bundle and ran it while the new worker installed behind it — `republishProfileIfStale`
lives in the sign-in effect, and the sign-in effect ran on the old code. Only the launch after
that ran the new bundle. And a PWA resumed from the switcher never navigates, so it never
checked for a release at all. So "sync on the latest version" meant *kill the app, open it,
kill it, open it*, and nothing Ben could do from his side would move it.

**Built.** Two hooks in `main.jsx`, nothing elsewhere:
- **Reload once when a new worker takes over.** `sw.js` already calls `skipWaiting()` and
  `clients.claim()`, so `controllerchange` fires on the page within seconds of a release being
  found. The page reloads once, and the reload goes through the new worker, whose cache holds
  the new `index.html`. Guarded two ways: a page that had no controller when it loaded (a
  first-ever install, or a hard refresh) is not reloaded, because it already runs the bundle it
  just fetched; and a `reloaded` flag stops a second reload.
- **Check for a release on return to the foreground.** `visibilitychange` → `visible` calls
  `registration.update()`. Browsers check for a new worker on navigation, which an installed
  app kept in memory for days never does. The check is a `HEAD`-sized fetch of `sw.js`.

Together: a release lands → the next launch or foreground finds it → the page reloads → sign-in
runs on the new bundle → the profile republishes → every friend's live board picks it up. The
same hook retires the reason behind the eight cache bumps on 13 September: an installed app now
runs a release on its first launch after it, not its second. The bumps themselves stay, since
the precached `index.html` is only replaced when the cache name changes.

**The cost.** A reload mid-session drops unsaved form state. The window is the few seconds
between a launch or foreground and the new worker activating, on a launch that follows a
release; a running hangboard timer in that window would restart. Accepted over the alternative
of every friend reading *not shared yet* for a launch.

- Cache v38 → v39.

**Seen in Chromium** against the built app on a throwaway static server, driving the worker
with Playwright: a first install loads once and does not reload; bumping the served `sw.js`
and launching again loads the old bundle, then reloads exactly once, with only the new cache
left; a foreground with nothing new does not reload; a foreground with a release waiting finds
it and reloads once. Harness in the scratchpad, not the repo.

## BTL-B44 — bottom tabs floating

**Merged 2026-09-18 on Ben's word — *"Push to main."* Not seen on a phone first; the check below still applies to the live site.**

**Cause.** The mobile bottom nav is `position: fixed` with `backdrop-filter: blur(12px)`.
WebKit has a long-standing compositing bug where a fixed element carrying a backdrop blur is
painted at a stale scroll offset after the document's height changes underneath it — a widget
collapsing or expanding, a sheet closing, the keyboard dismissing. The page scrolls, the bar
does not follow, and the blur layer smears the content it used to sit over. That is exactly the
screenshot: bar mid-page, whited-out band beneath it, "V4 / V5" rows showing through the edge.

**Fix — `src/components/layout/Nav.jsx`.**
- `backdropFilter` removed from the bottom nav. Background is now solid `#ffffff` instead of
  92% white; there was almost nothing to see through it anyway.
- `transform: translateZ(0)` on the bar so it has its own compositing layer and is repositioned
  with the viewport rather than repainted with the page. A transform on the fixed element itself
  does not break its fixed positioning — only a transform on an ancestor does.
- The sticky top header and the desktop nav keep their blur — the bug is specific to `fixed`.
- Comment in the JSX says why, so nobody adds the blur back for looks.
- Cache v33 → v34 so installed phones drop the old bundle.

**668 tests, 0 lint errors, build clean.** The bug is intermittent and only reproduces on iOS, so
it is not verified on a phone. Check on the preview deploy: open the Dashboard, expand and collapse
the Boulder widget a few times mid-scroll, open and close a log sheet, and the bar should stay on
the bottom edge throughout.

Released the same day on Ben's instruction.
