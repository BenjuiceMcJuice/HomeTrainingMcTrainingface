# 2026-08-19

## Schedule reminders — step 1: a reminder time per schedule entry

Picking up `docs/specs/betalog_reminders_spec.md`. Both reminder routes (calendar feed, web push)
were blocked on the same gap: `ScheduleEntry` had days but no time of day and no timezone. That's now
closed.

### The decision that shaped it

The spec left open whether reminders should be **one per entry** or a **daily digest**. Ben: one per
timed thing, so a morning and an evening reminder are both possible. So each entry carries its own
`remindAt` — hangboard 07:00 Mon/Wed/Fri and gym 18:30 Tue/Thu is two entries and two alerts, no
digest, no bundling. Both routes now build on that shape: one `VEVENT` per timed entry for Route A,
one push per timed entry for Route B.

### Files changed

- **`src/lib/types.js`** — `ScheduleEntry` gains optional `remindAt` ("HH:MM" local, 24h) and `tz`
  (IANA). Both optional, so existing schedules keep working untouched.
- **`src/lib/reminders.js`** *(new)* — `isValidRemindAt`, `localTimeZone`, `withReminder`,
  `sortByRemindAt`. Pure, no React imports, so `storage.js` and later the Worker can both use it.
- **`src/lib/__tests__/reminders.test.js`** *(new)* — 14 tests. All pass.
- **`src/hooks/useSchedule.js`** — `setReminder(id, remindAt)`, and `addEntry` takes an optional time.
- **`src/components/routines/ScheduleCard.jsx`** — bell + `<input type="time">` per entry with a
  Clear control, and an optional time on the add form.
- **`src/components/dashboard/ScheduleNotice.jsx`** — shows the time against each routine and orders
  due-today entries by it, untimed last.

### Decisions worth recording

- **Clearing deletes the keys, it doesn't null them.** `withReminder(entry, '')` removes `remindAt`
  and `tz` entirely. The spec says "absent = no reminder", and the `.ics` builder will test for
  absence — a stored `null` would have been a trap later.
- **No separate "Remind me" switch.** An empty time *is* the off state. One control, not two, and
  reminders stay off until a time is deliberately set.
- **`tz` is captured on every set**, not once globally, so moving timezone and re-saving fixes itself.
  Without it a Worker running in UTC is an hour out for half the year.

### Verified

`npm run build` clean. `npm run lint` 0 errors (16 pre-existing warnings). The 14 new tests pass; the
4 known MET/calorie failures in `stats.test.js` are untouched and still open.

Driven in a real browser (Chromium/Playwright, temporary local auth bypass, reverted): set 07:00 on

"Due today: Max Hangs · 07:00 / 7:3 Repeaters · 18:30", sorted morning-first even though the evening
entry was stored first.

### Known limits (pre-existing, not introduced here)

The schedule caps at 3 entries and `ScheduleCard` won't schedule the same routine twice — so "the
same routine, morning and evening" isn't expressible. Two different routines at two times is. Small
change to lift either if it matters.

## Route A decisions settled (design discussion, no app code changed)

Talked through how the calendar feed behaves in practice. Recorded in the spec:

- **Only timed entries get a `VALARM`.** An untimed entry becomes a silent all-day event — visible,
  never buzzes. Corrects an earlier suggestion of a 09:00 alarm for untimed entries: clearing a time
  is how a user says "stop reminding me", so it must not produce a different nag.
- **`remindFrom` anchors `DTSTART` once**, stored when the reminder is set, so the feed is stable
  between refreshes instead of shifting on every request.
- **Stable `UID` per entry** so edits update the event and deletions remove it.
- **KV mirror on save** is the step that makes any change reach the feed — the Worker never reads
  Firestore.
- **One feed URL per user**, shared across devices; revoking the token kills all subscriptions.
- **Refresh lag accepted.** iOS decides when to refetch; can be hours. The schedule is a weekly
  pattern that rarely changes, so eventual correctness is fine. A deletion shortly before a reminder
  may still fire once.
- **Route B deferred.** Not a now problem.

Also confirmed as fine, not worth changing: one entry per routine, 3 entries max.
