## Widget system — phase A: the shell, properly

First phase of `docs/specs/betalog_widget_system_spec.md`. Scope is exactly what the spec gives
phase A: make the whole header the collapse control, move the timeframe chips out of the headers and
into the bodies, and restore the calendar's full-width header. No new data, no new widgets, none of
the three open decisions touched.

### The whole header row is the tap target

`WidgetShell.jsx` — the row is now a real `<button>` with the header content inside it and the
chevron as a decorative `<span>`; `min-h-[44px]` puts it over the touch-target threshold that the
old ~24px chevron missed. Hover moves to `group-hover` on the chevron, so nothing looks different
until you tap.

In edit mode the row renders as a plain `<div>` again — same rule as before, a tap meant for the
drag handle must not fold the card.

This restores what `ActivityCalendar` had before declutter phase 2 replaced its full-row toggle with
the small chevron, and it gives the same affordance to the other four collapsible widgets rather than
only putting the regression back.

### Chips moved into the bodies

A `<button>` header means no buttons in the header — nested buttons are invalid HTML and ambiguous
to tap. Two cards had them:

- **Cardio** — the `7d / 90d` chips now head the body. The header keeps the count and total duration
  and gains a plain-text window label (`2 sessions 7d`), so a collapsed card still says which window
  its number covers.
- **Alcohol** — the chips move off the timeline's value row onto their own row at the top of the
  body, matching the anatomy diagram and the cardio card. The `-1 vs prev` delta keeps its
  right-hand slot.

`LevelCard` already worked this way, so it is untouched; the calendar's month stepper was already in
its body.

**One copy fix on the way past:** the cardio card said "No sessions this week" whatever the window
was selected — it now reads "No sessions in the last 7d/90d".

Dropped the unused `ChevronDown`/`ChevronUp` imports from `ActivityCalendar`, left over from before
it used `WidgetShell`.

## Widget system — phase B: one vocabulary

Ben chose **per-card, persisted** for the window question, so phase B was buildable. Built on
`claude/widget-thingy-phase-a-1hy78q` — the branch name is now a phase behind, but it is the
designated branch for this session, so the work stays on it.

### Windows are a persisted, per-card thing

New `src/lib/widgetWindow.js`, deliberately shaped like `widgetCollapse.js`: `WINDOW_OPTIONS` per
card, `WINDOW_DEFAULTS` (90d everywhere), `getWindow`, `setWindow`, `windowDays`. State lives in
`profile.widgetWindow`, beside `widgetCollapsed`, so it syncs across devices for free.
`hooks/useWidgetWindow.js` is the component-facing wrapper.

`getWindow` validates the stored value against what the card currently offers and falls back to the
default when it does not match. That is not defensive padding — cardio's `7d` chip disappears in
this phase, and anyone who had it selected has a stored `7d` that no longer exists.

14 unit tests in `src/lib/__tests__/widgetWindow.test.js`.

### One vocabulary

- **Cardio** — `7d / 90d` becomes `30d / 90d / 12m`, defaulting to 90d rather than 7d. Its window
  now comes from `filterSessionsByDays` like everywhere else, not `daysAgo(days - 1)`.
- **Alcohol** — `30d / 12w / 12m` becomes `30d / 90d / 12m`, and the chips now mean *window*, not
  bucket size. The card derives granularity: 30d → daily bars, 90d → weekly, 12m → monthly, via a
  new `ALCOHOL_WINDOW_MODE` map in `stats.js`.
- **Level cards ×2** — chips unchanged (`90d / All time`, a different question), but the choice
  now persists instead of resetting on every reload.
- **Gym** — `daysAgo(89)` replaced with `filterSessionsByDays(…, 90)`. No chips: it has no body to
  put them in until phase D.

**Weekly buckets went 12 → 13.** A chip that says `90d` has to cover 90 days, and 12 Monday-aligned
weeks only cover 84. Seven timeline tests moved index (the current bucket is now 12, not 11) and the
average-per-week expectation changed with the longer window — all in `stats.test.js`.

**Cardio's visibility gate changed** from "any cardio in the last 90 days" to "any in the last 12
months". Offering a 12m chip while hiding the card from anyone without a recent session would have
hidden it from exactly the people that chip is for. Chips for empty windows render disabled, as the
`7d` chip already did.

## Widget system — phase C: the chart component

Extraction only. The alcohol timeline's bars become something cardio and gym can use in phase D,
and the dashboard does not change by a single pixel.

### Split in two

- **`src/lib/barChart.js`** — the arithmetic, pure and testable: `buildBarGeometry(values, opts)`
  returns the scale, each bar's height, which bars are over the guideline, where the guideline line
  sits, and which bucket carries the peak label. `labelledIndices(count, step)` moved here too,
  generalised from the alcohol card's mode-specific version.
- **`src/components/dashboard/BarTimeline.jsx`** — the rendering: bars, guideline, peak value label,
  tap-to-select, and the x-axis labels in both styles (every nth bucket, or ends-and-middle for
  daily buckets, which are too many to label individually).

`AlcoholFreeCard` now maps its buckets to `{key, label, fullLabel, value}` and passes its colours,
guideline and label style in. The card lost ~70 lines and all of its geometry.

Putting the arithmetic in `lib` rather than testing the component was deliberate: vitest runs in
`node` here, with no jsdom or testing-library, and the interesting part of a bar chart is the
numbers. 13 tests in `barChart.test.js`, several of them pinning behaviour that was previously
implicit — the 3px floor under a tiny value (so a real bar never renders shorter than the "nothing
logged" stub), the last-peak-wins rule when the maximum repeats, and the guideline dropping out on
an empty window.

## Widget system — phase D: cardio and gym charts

The payoff from C. Both one-line cards gain a body built on `BarTimeline`, so they answer *am I
doing more or less than I was* rather than just how many times.

### One timeline builder for all three charts

`stats.js` grew `buildBucketScaffold(mode)` — the empty buckets for a window, oldest first, last one
containing today — pulled out of `buildAlcoholTimeline`, which now uses it. On top of that sits
`buildValueTimeline(items, mode, valueOf)`: the general form, summing any dated records into those
buckets. All three charts therefore cover the same span and label their axes identically, which is
checked directly by a test asserting the cardio buckets match the alcohol ones key for key.

The alcohol timeline's own tests all passed through this refactor untouched — that was the point of
having them.

Also renamed on the way through: `ALCOHOL_TIMELINE_MODES` → `TIMELINE_MODES` and
`ALCOHOL_WINDOW_MODE` → `WINDOW_BUCKET_MODE`, since neither is alcohol's any more.

### The two cards

- **Cardio** — minutes trained per bucket, in the card's teal. Beneath it the existing activity
  breakdown, kcal line and goal bars, unchanged.
- **Gym** — sets per bucket, in the card's blue, and it becomes a proper collapsible widget:
  `WidgetShell`, `30d / 90d / 12m` chips, and a header carrying sessions, window and total sets.
  Beneath, the existing "most-trained muscle group" line, which is more useful next to a trend.

Both support tap-a-bar, matching alcohol: the summary line becomes that bucket's readout
("week of 3/8 · 1 session · 5 sets") and returns when you tap it again.

`gymStats` joins `COLLAPSE_DEFAULTS` (folded — it has a chart now) and `WINDOW_OPTIONS` /
`WINDOW_DEFAULTS` (90d). Its visibility gate matches cardio's: any gym session in the last 12
months, so the longest chip is reachable.

**Finding 5 is closed.** Six of nine widgets fold; the three that do not — training load (whose
7d:30d windows *are* the metric), coach tip (a sentence) and weight (a number) — have nothing to
hide, which is the rule the spec wanted made visible.

### One unplanned alignment

The taller bodies exposed something: on cardio, gym and the two level cards the icon circle sits
outside `WidgetShell` in a `flex items-center` row, so with a chart in the body it floated in the
vertical middle of the card, level with the bars rather than the headline. Changed those three files
to `items-start`, which is what the spec's anatomy shows (`ICON  HEADLINE`). The weight card keeps
`items-center` — it has no body, so there is nothing to align against.

## Widget system — phase E: the calendar

Ben left the calendar-detail decision to me, so: **tap-a-day**, which is what the spec recommends.
It is the smallest of the three options, it answers "what happened when" directly, and it leaves the
week-strip available if the month grid turns out to be the wrong shape in practice. Intensity-by-dot-
size is the one I would drop entirely — dot area is a bad encoding for volume and the readout says
it in words for free.

### It is a real widget now

`activityCalendar` joins `DEFAULT_ORDER`, `renderWidget` and `WIDGET_OPTS`, and the hardcoded render
after the Edit layout button is gone. It reorders, switches off and counts against `MAX_WIDGETS`
like everything else — 9 widgets defined against a limit of 10.

Deliberately **not** an opt-in key: the calendar has always been on screen, so it defaults visible
and existing users see no change. Only the two phase-D-era cards stay opt-in.

### The two bugs behind the phase

**Cardio had no dot.** `DOT_COLOR` and `TYPE_COLOR` covered gym, climb and hangboard only, so a swim
or a run left the day completely blank and the legend never mentioned it. Cardio is now teal
(`#0d9488`, matching its card) with a legend entry. A type in neither map falls back to a neutral
dot and a neutral cell — previously an unknown type rendered as *nothing*, which is how cardio went
missing unnoticed in the first place.

**Collapsed, it said nothing.** The header was the words "Activity calendar", which fails the
declutter's contract 1. It now reads `ACTIVITY 18 sessions August` with a breakdown line
underneath — "7 cardio · 5 gym · 4 climb · 2 hangboard" — for whichever month is in view.

### Tap a day

Day cells became buttons. Tapping one prints a line under the grid: **"Wed 19 · Swim 45m"**,
"Thu 4 · Gym 12 sets · 3 climbs to V5 · 2 units". Tapping again clears it back to the hint. Stepping
months clears the selection.

The text comes from `describeDay(date, sessions, drinkLog)` — pure, in `stats.js`, 10 tests. It reads
grades off the right scale per discipline (V for boulder, French for rope), counts only *sent* climbs
towards the day's grade, skips gym exercises marked not done, and names a session type it has never
heard of rather than dropping it.

## Loose ends cleared

The two follow-ups noted during phases E and F, plus a third the verification turned up.

**1. The picker saved during render.** `WidgetPicker.toggleWidget` called `saveProfile` *inside* the
`setWidgets` updater. That makes saving a render-phase update of a component above this one, which
is what React was warning about — and an updater that writes to storage can legitimately be re-run.
The save moved out; the toggle now computes the next map from state it already has, sets it, then
saves.

**2. `CalorieBalanceCard.jsx` deleted.** Imported nowhere, dead since before this work.

**3. Toggling any widget silently hid gym and cardio stats.** Found while checking fix 1 in the
browser: nine cards on screen became five after one unrelated toggle.

The two views of "is this widget on" disagreed. `Dashboard.showWidget` is `prefs[key] !== false` —
default on. `WidgetPicker` carried an `OPT_IN_KEYS` list making `gymStats` and `cardioStats` default
*off*, added when they were new so nobody was pushed over `MAX_WIDGETS`. So the Dashboard rendered
them while the picker considered them off, and the first toggle of *anything* wrote the picker's
whole map — including `gymStats: false, cardioStats: false` — and two untouched cards disappeared.

Fixed by dropping `OPT_IN_KEYS`: the picker now defaults on, matching the Dashboard. The limit
argument is also gone — nine widgets against a cap of ten, so all-on fits. Anyone who deliberately
switched a card off keeps it off, because that is a stored `false`.

Verified in the browser: nine drag handles before any toggle, eight after switching one widget off,
nine again after switching it back, `dashWidgets` storing what you would expect, and no React
warnings at any point. Lint clean, 182 tests, build green.

## Cardio calories ignored the selected bar

Ben spotted it on the live card: tap a bar and the summary line follows it ("week of 15/6 · 10
sessions · 8h 30m") while the calorie line underneath sits at "~13,702 kcal burned" — the whole
90-day total. The number does move when you change window, so it was not frozen outright; it simply
had nothing to do with the bar you had selected.

Cause: `buildStats` totalled calories across the window, and the card rendered that total
unconditionally. Every other selectable readout on the dashboard swaps to the picked bucket — the
alcohol card's kcal already did.

Fixed by bucketing calories the same way the bars are. The per-session estimate moved out of
`CardioStatsCard` into `estimateSessionKcalMid(session, sortedWeights, profileWeight)` in `stats.js`,
which the card now uses twice: once summed for the window total, once through `buildValueTimeline`
for a per-bucket series. Selecting a bar reports that bucket; clearing the selection restores the
total. A bucket with sessions but no usable estimate says so rather than showing "~0 kcal".

The extraction paid for itself in testability — 6 tests on a function that had been 25 lines inline
in a component, including the one behaviour most likely to rot silently: a session is costed at the
body weight recorded *on or before* it, so an old session is not priced at today's weight.

Verified in the browser: window totals 30d/90d/12m → ~10,683 / ~32,067 / ~102,471 kcal; three
different bars at 90d → ~2,080, ~3,687, ~1,849, each matching its own session count and duration;
clearing the selection returns exactly the unpicked total. Lint clean, 188 tests (was 182), build
green.

Merged straight to `main` — restoring intended behaviour on a broken readout, per the release policy
in `CLAUDE.md`.

## Calendar day readout: "50m" was fifty minutes

Ben read "Thu 20 · Sport 50m" on the live calendar as fifty *metres*. It was fifty minutes —
`describeDay` printed `cardioDurationMins + 'm'`. On a line that sits beside swim and run distances
that abbreviation was never going to survive contact.

Two changes to the cardio part of the readout:

- **`min` spelled out** — "Sport 50 min".
- **Distance leads where it was logged**, because it is usually the thing you set out to do:
  "Run 5.0 km · 28 min", "Swim 800 m · 40 min", "Swim 800 m" when only a distance exists. Formatting
  matches `fmtDist` (≥1 km to one decimal, otherwise whole metres) and `deriveSessionMetres` handles
  pool lengths and miles, so 32 × 25m lengths reads as 800 m and 3 miles as 4.8 km.

**Calories were considered as the unit and rejected**, for the readout and the chart both. A kcal
figure is an estimate of METs × weight × time, not something logged: the MET correction on the 19th
retroactively changed every historical figure, and a new weight entry shifts the past too. A
calendar line answering "what did I do" wants the session, not its consequence — calories already
sit under the cardio chart as a footnote, which is the right weight for an estimate.

Left unbuilt by choice: a `mins / kcal` value toggle on the cardio chart. It is cheap now that
`BarTimeline` and `estimateSessionKcalMid` exist, and kcal is the better second unit than distance
(km cannot be summed across swim, run and cycle in one bar) — but Ben's call was that the card would
be too busy, and he is right that it already carries chips, bars, a summary and goal rows.

Verified in the browser across five days: "Thu 20 · Sport 50 min", "Wed 19 · Run 5.0 km · 28 min",
"Tue 18 · Swim 800 m · 40 min", "Mon 17 · Swim 800 m", "Sun 16 · Gym 2 sets · 2 climbs to V4 ·
2 units". Lint clean, 190 tests (was 188), build green.
