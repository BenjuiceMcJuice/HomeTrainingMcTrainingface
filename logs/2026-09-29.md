## BTL-B110 — venues as a shared registry (branch `claude/venue-registry`)

Ben: *"I'm still not totally happy with the venue picker it seems a bit random (maybe cos I set
venues when at home to test). I'd like it to be either location based or a picker so you can pick
from a list of options based on entered data. No dups. This way we can lock down feature la to
location perhaps? Or open up location 'admins' / teams maybe?? … I see this as barely impacting
the UI but the back end only. Have a really good think."* Then: *"Can you build it now?"*

**Why it felt random.** A venue was a string with a mutable pair of coordinates in
`profile.venues`, and `recordVenue` moved them to the phone's fix on every save dated today.
Testing from home walked Redpoint and Flashpoint to the house: at home the logger said a wall was
12 m away and prefilled it; at the wall nothing was within 300 m, so the chips were the five most
recent names, reordered every session, with spelling twins. BTL-B59 had named the cause.

**Decided** (the reasoning is in the spec §9 and the backlog's decisions section): a venue is a
document in `venues/{id}` readable by every signed-in user — name, `nameKey`, position + geohash
set once, `admins: []`; `session.venueId` beside `location`; `profile.venues` repurposed as a
cache of `{id, name, lat, lng}` so the chips work offline and cost nothing; the pre-registry
entries dropped on load and cloud merge. A flat collection, not `gyms/{g}/centres/{c}`: a venue
exists before a gym claims it. Position never moved by a save — B59's two options both rejected,
the mechanism deleted. Adding is an explicit, named-as-shared tap; a typed name never added stays
private text, which is what keeps a home wall off a public list.

**Built.**
- `src/lib/venues.js` — rewritten, pure, 43 tests: `cleanName`/`venueKey`; geohash encode
  (checked against the spec's reference hashes) and `geohashCells(pos, 300)` — the one to four
  6-char cells a 300 m radius reaches, no dependency; `newVenueDoc`, `placedFields`, `venueRef`,
  `nameProblem`, `duplicateCandidates`; the cache (`cacheVenue`, `migrateVenueCache`,
  `hasLocatedBefore`); the log's venues (`venuesFromSessions` groups by `venueId` else by name,

- `src/lib/storage.js` — `createVenue`, `placeVenue`, `getVenue`, `findVenuesNear` (one prefix
  query per cell, haversine-filtered on the client), `searchVenues` (`nameKey` prefix, limit 10);
