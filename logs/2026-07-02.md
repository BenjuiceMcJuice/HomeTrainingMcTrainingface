# 2026-07-02

## RGP integration & retention strategy review

**Files changed:** `docs/strategy/betalog_rgp_integration.md` (new), `docs/strategy/betalog_vision.md`, `docs/strategy/betalog_partner_overview.md`, `CLAUDE.md`, `DEVLOG.md`

### What was done
- Reviewed the app from a climbing centre's perspective: what it offers a gym today, what's missing for a centre deployment
- Researched the Rock Gym Pro API (read-only REST, Basic Auth, endpoints: facilities / checkins / customers / bookings / invoices; no webhooks; no bulk customer listing)
- Wrote `docs/strategy/betalog_rgp_integration.md` — the full approach for linking RGP → Firestore:
  - Recommended architecture: Cloudflare Worker cron sync (keeps Firebase on Spark, no client-side secrets)
  - Consent-first member linking (email match, explicit opt-in)
  - Retention playbook: first-visit journey, check-in-linked sessions, rewards/benefits engine, lapse detection
  - Revenue options: coaching funnel from performance data, membership upsell from visit patterns
  - GDPR section: gym = controller, BetaLog = processor, data minimisation rules
  - Phased delivery: Phase A needs no API at all (QR onboarding, location stamping, manual challenges)
- Updated vision doc: new "Gym systems integration" section, backlog and decision log entries
- Updated partner overview: retention & revenue section for the gym pitch, status table rows

### Key decisions
- RGP credentials must never ship in the client — read-only key still exposes the full member database
- Server-side sync via Cloudflare Worker preferred over Firebase Cloud Functions (avoids Blaze upgrade) and over Zapier (per-task costs, weak transforms)
- Rewards redemption is app-shows-code / staff-validates — RGP API is read-only so BetaLog cannot write discounts into the POS
- Store RGP data under `gyms/{gymId}/members/{rgpCustomerId}`, minimised (no payment data, hashed email until a member links)

## Follow-up: multi-centre aggregation + AI insights

**Files changed:** `docs/strategy/betalog_rgp_integration.md` (sections 4b, 4c, phases, decision log), `docs/strategy/betalog_vision.md`, `docs/strategy/betalog_partner_overview.md`

New input from the centre: they run a **separate RGP install per centre** and
already collate the data via the API by hand. Added to the strategy:

- **Section 4b — multi-centre aggregation:** Worker syncs N RGP instances
  (per-centre credentials + watermarks), identities joined across installs by
  email hash (`members/{memberId}` with `rgpIds` map — same person has different
  RGP customer IDs per centre), nightly rollups into `gyms/{gymId}/analytics/*`.
  BetaLog becomes their collation layer; "replace or feed" their current setup
  is a pilot decision.
- **Section 4c — insights & AI analysis:** pattern catalogue (cohort retention
  curves, visit decay, first-visit→member conversion, peak-load heatmap,
  cross-centre usage, booking funnel) computed deterministically; AI adds the
  narrative layer in three tiers:
  - Tier 0: Claude on their existing exports (claude.ai / Claude Desktop + MCP)
    — zero build, offerable today with or without BetaLog
  - Tier 1: scheduled Worker job → Claude API (`claude-opus-4-8`, aggregates
    only, <$1/report, Batch API halves it) → monthly narrative briefing
  - Tier 2: "ask your data" staff chat via read-only aggregate tools (Pro tier)
- **Privacy rule:** AI layer reads only `analytics/` rollups — PII structurally
  cannot cross the wire; Tier 0 is the gym's own controller decision.
- Phases updated (A½ Tier-0, Phase B multi-instance + rollups, Phase C Tier-1,
  Phase C+ Tier-2); open questions now probe their current collation in detail.
