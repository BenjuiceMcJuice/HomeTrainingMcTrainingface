### BTL-B32 — Settings › Account › Delete account…

A red *Delete account…* button under *Sign out* opens its own sheet with three steps:

1. **What goes** — the log (with its session count), goals/routines/schedule/health/venues, the
   friend profile and friends' lists, the calendar feed and this device's reminders, the sign-in,
   this device's copy. Says what it cannot reach (feedback, reminders from other devices). An
   *Export your data first* button reuses Settings' JSON export.
2. **Are you sure?** — no undo, no backup, signing out keeps everything; a tick box must be ticked.
3. **Last check** — type DELETE, then sign in again (password field for email accounts, Google
   popup otherwise). *Keep my account* is on every step.

The fresh sign-in comes **before** anything is deleted. Firebase refuses `deleteUser` for a stale
sign-in, and discovering that after the Firestore documents were gone would leave a live, empty
account. Order after that: revoke the calendar feed and this device's push subscription
(best-effort), take the uid off every friend's list, delete the public profile, the friend code,
the main document, then the auth user, then every `il_` localStorage key, then reload.

Google sign-in in an installed iOS app cannot open the popup — the same limit as sign-in — so the
sheet says to do it from Safari instead of offering a button that hangs.

Files: `lib/accountDeletion.js` (new — order of operations, reauth, pure helpers),
`components/layout/DeleteAccountSheet.jsx` (new), `lib/storage.js` (`deleteCloudData`,

function), `firestore.rules` (owner may delete their own friend code — **needs deploying, BTL-B72**),

## BTL-B74 — bouldering competitions, planned

Ben, from a cloud session: *"I want to plan out a way in which an admin (climbing gym say) can
setup a bouldering competition. This would be on a date and at a location. Using a scoresheet that
people can virtually enter. Yes plan this out."*

Planning only — `docs/specs/betalog_competitions_spec.md`, no code. What the plan settles and why:

- **The scorecard is the feature.** An organiser creates a comp (name, date, times, venue from the
  existing venue picker, notes), builds a scoresheet of numbered problems with points and an
  optional grade (a generator does *30 problems, points by circuit* in one go), opens entries and
  gets a join code `CP-XXXXX` plus QR. Entrants join by code, pick a category, tick Flash/Top on
  their phone during the live window, and watch a leaderboard. Organiser closes; results are final.
- **No gym table first.** The data model's `gyms/…/staff` tree is still unbuilt and would make the
  first comp wait on console onboarding. Proposal: any signed-in user can create a comp and is its
  organiser (`organisers: [uid]`), the friend-code pattern; `gymId`/`centreId` reserved as nulls for
  when the tree exists. Noted against BTL-B22.
- **Storage.** New top-level `competitions/{code}` with the join code as the document ID so join is
  a `get`, never a `list` (same reasoning as `friendCodes`); `entries/{uid}` subcollection, one card
  per entrant, writable only by its owner, only `ticks`, only while `status == 'live'`. Scores are
  never stored — computed on the client from ticks by pure `lib/competition.js`, so nothing can be
  forged by writing a number. Entrant's card mirrored to `il_compCards` first for a basement with
  no signal (the SDK has no persistent cache here). Rules drafted in the spec; first rules tests in
  the repo proposed via the emulator.
- **Three formats specified, one built first**: points/best-N with optional flash bonus (the
  gym-scorecard norm); top-zone-attempts and shared-points shaped into the same `CompFormat` union
  for later.
- **Honesty.** Ticks are self-reported as on paper; the board's caption says *scores as entered by
  climbers*. Organiser corrections record before/after with a note the entrant sees. Nothing
  touches the pyramid until the entrant taps *Add to my log*, and then graded problems only.
- **Where.** A Competitions screen reached like Friends (not a Plan tab, not a sixth bottom tab), a
  Dashboard card, a Log-page banner while live, and `/comp/{code}/board` for the gym TV.
- **Reads on Spark** worked through: a 30 s throttle on the entrant's board; a Worker-published
  summary is the step up if comps get big.

Seven questions for Ben in §10 (who may organise, first format, log integration, placement, live
board visibility, display name, walk-ins), each with a recommendation. Backlog row BTL-B74,
Blocked on them. CLAUDE.md doc index updated. No DEVLOG entry — nothing shipped.

### Second pass — ready for build

Ben: *"So mostly agree. How easy would this all be to change later. Also with graded climbs could
they also be logged for the climber when done?"* Then: *"I'd want the comp specific 'sessions' to
be slightly different though with comp style logging like attempt / zone / top / number of gos etc
(max of x value — to be set when creating comp). The setter can grade each climb but can toggle
whether to show the grade or not. Spec out a basic version please in detail ready for build."*

Spec rewritten. What changed from the morning's draft:

- **Scoring is one format**: per comp `maxAttempts` (the stepper stops there), a per-go percentage
  table for a top (`[100, 80, 60, 50, 50]` default), a zone percentage (25), optional best-N. The
  three-format union is gone; IFSC-style flat scoring is every percentage at 100 with the tiebreaks
  (tops, zones, fewer goes).
- **The card is a session in the log from the first go** — `session.comp` holds the card, the
  sheet and the scoring as last seen; `session.climbs` is *derived* by `climbsFromCard` and never
  edited: graded top on go 1 → flashed, go n → sent with `attempts: n`, graded tries → attempt
  with the real count, zones and ungraded problems → no climb. First real use of `Climb.attempts`
  (BTL-B9); checked that `stats.js` and `pyramid.js` count rows, not the field. The entry document
  is a mirror, re-pushed whole on reconnect. History opens the scorecard for a live comp session,
  hides delete, never opens the climb editor on one.
- **Card controls through one pure reducer** `applyCardAction` with the invariants `top ⇒ zone`,
  `zoneAttempt ≤ topAttempt ≤ attempts ≤ maxAttempts`, tested.
- **Hidden grades cannot be on an entrant's phone**, so `problems[].grade` is null where
  `showGrade` is false and the real grade sits in `competitions/{code}/private/grades`
  (organisers only); Close copies them back and the entrant's device re-derives the climbs.
- **Corrections are void-with-note only**; scoring and points frozen once live.
- **Reversibility answered in chat**: nearly everything is a rule line or a pure-function branch
  because scores are never stored; the one-way door is the climber's log, which is why the card
  writes into it with derived climbs that can be recomputed. `schemaVersion` added to the comp doc.
- Gym-screen route and walk-ins deferred; the seven questions closed in §12 on Ben's "mostly
  agree", two of them overtaken by the new model.
