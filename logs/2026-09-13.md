## BTL-B10 — a gym session scores by what was in it

A flat 2 made ten minutes of ankle alphabet count the same as an hour of lifting, and it showed:
backfilling the log scored **w/c 13 April at 100, EXCELLENT**, off five consecutive days of ankle
rehab physio. `difficulty` could not fix it — those were logged as 2 like everything else — so the
score reads exercise count, the one thing that actually separates rehab from training.

Bands, not a per-exercise rate: the difference worth capturing is rehab vs training vs a full
session, not one extra accessory lift. **The middle band is the old flat value**, so an ordinary gym
session is unchanged and only the extremes move. That week goes 10 training points → 5, against a
target of 9.

**An existing test caught the first version.** It asserted a bare `{type:'gym'}` scores 2; my first
pass scored it 1. That would have inferred "rehab" from an empty exercise list — absence of evidence
treated as evidence of a small session. A gym log with no exercises is missing detail, so it keeps
the old value. `SCORE_VERSION` 1 → 2; sealed weeks keep version 1 and are never rescored.

## BTL-B14 — which build is this device running?

Three facts, because no one of them answers the question. **Build** is the commit Cloudflare built
from and changes every deploy. **Cache** is read from the *running* service worker rather than from
source — a device serving a stale bundle has the stale worker too, so asking the worker is the
difference between what should be installed and what is. **Version** is last, because
`package.json` only changes when somebody bumps it.

`CF_PAGES_COMMIT_SHA` has no `VITE_` prefix so Vite will not expose it on its own; injected via
`define`. Verified end to end by building with the variable set and grepping the bundle for it.
eslint gains two *scoped* blocks — node globals for `vite.config.js`, the injected constants for
`buildInfo.js` — rather than loosening globals everywhere.

**Two faults in that.**

  weeks to move up a grade (a typical time — your log has no grade change to measure yet)."*

With the rate fixed, the 60-day conversion is now most of the date. It is the stated default, not
measured, and the new line says so, which is the next thing for Ben to judge.

## Goals rework — "I've already sent it, why is it 2/5?"

Ben, on a *send a 6a* goal due 30 September, with a full pyramid and the 6a sent the week
before: *"the 1/5 dot achievability score seems broken … it shows as 2/5 dots. Also I've already
achieved that goal."* Worked back from the code, the 2 was exact arithmetic:

```
readiness        base complete                      5
shortfall        0                                  0 days
conversion       French default 60 x Intermediate 0.8   48 days
deadline         13 -> 30 Sept                      17 days
ratio            48 / 17 = 2.8, over 2.5            dock 3
mark                                                2/5
```

Two faults, one above the other. **The forecast charged time to move up to a grade already
climbed** — `sentTarget` was on the readiness object and nothing read it. And **the send did not
count**, because yesterday's rule only counted sends dated after the goal was set; a 6a from the
week before was invisible to auto-achieve, so the goal sat active with a green "1 send at 6a
already" line under a red 2/5.

On `feat/goals-achieved-rework`, not merged:

- **A send inside the pyramid window is a send.** `goalEvidence` replaces `goalMet` as the thing
  auto-achieve reads (`goalMet` stays as its boolean). It returns *what* achieved the goal — the
  earliest qualifying send with its date, the base grade, or the value — and `Goal.achievedBy`
  stores it. `achievedDate` is now the evidence's date, so a send goal sits in History on the day
  of the send.
- **The sheet refuses a goal the log has already met**, with the reason: *"Already done — you sent
  6a on 3 Sep. Aim higher, or switch to Become a 6a climber."* A *become* goal is only refused
  when the base is already there; one send does not own a grade, which is the whole point of the
  second kind.
- **A sent target charges no conversion time.** `forecastReady` reads `readiness.sentTarget`;
  `conversionDays` is 0 and `basis.pace` is `'sent'`. The steps line says *"…and V5 is already
  sent"* instead of quoting a typical time. Ben's case now reads 5/5.
- **Achieved goals are in the History feed** — a read-only green row on the day of the evidence,
  sorted after the session that earned it. Goals stay managed in Plan › Goals.
- **The Dashboard climbing cards draw the pyramid with no goal set**, for the rung above the base
  (or above the project when there is no base), labelled *next up · no goal set*. No deadline, so
  no dots; the forecast line still shows.
- **Auto-achieve re-runs when goals change** — before, a goal set against a send already in the log
  waited for the next session save.
- **The readiness label takes the dots' colour.** Two red dots beside a green "Base complete" was
  one row with two verdicts. The words are unchanged.
- **The last 90-day count is gone** — the Dashboard goal line now counts sends over the pyramid
  window like every other climbing reading.

**Left open.** BTL-B33 narrows (only the "own it" fill is still unmodelled). **BTL-B34** filed for

## BTL-B33 — an Own goal forecasts the row it is actually waiting on

An *Own 6c* goal ticks off when the base *reaches* 6c: eight credited sends on the 6c row. The
forecast only ever projected the rows *under* the target — right for a Send goal, and the same date
for an Own goal on the same log, which understated it by the whole top row.

`forecastReady` now takes the goal's `kind`. For `become` it adds a third step: the target row's
shortfall (`OWN_SENDS`, the shape's widest row, minus credited sends there) at the rate this
athlete sends that grade over the same span. With no sends at the grade yet the base rate stands
in and `own.source = 'base'` says so — the steps line reads *"at your rate on the grades below"*
rather than pretending to have measured a grade never climbed. Headline: *"Own 6c around …"*. The
weekly what-if counts the row too, so the lever and the verdict agree. `readGradeGoal` passes
`kind` through from all three callers; `goalScore` needed nothing, it reads `daysToReady`.
