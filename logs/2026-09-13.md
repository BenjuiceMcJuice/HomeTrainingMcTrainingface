## BTL-B10 — a gym session scores by what was in it

A flat 2 made ten minutes of ankle alphabet count the same as an hour of lifting, and it showed:
backfilling the log scored **w/c 13 April at 100, EXCELLENT**, off five consecutive days of ankle
rehab physio. `difficulty` could not fix it — those were logged as 2 like everything else — so the
score reads exercise count, the one thing that actually separates rehab from training.

Bands, not a per-exercise rate: the difference worth capturing is rehab vs training vs a full
session, not one extra accessory lift. **The middle band is the old flat value**, so an ordinary gym
session is unchanged and only the extremes move. That week goes 10 training points → 5, against a
target of 9.

**An existing test caught the first version.** It asserted a bare `{type:'gym'}` scores 2; my first
pass scored it 1. That would have inferred "rehab" from an empty exercise list — absence of evidence
treated as evidence of a small session. A gym log with no exercises is missing detail, so it keeps
the old value. `SCORE_VERSION` 1 → 2; sealed weeks keep version 1 and are never rescored.

## BTL-B14 — which build is this device running?

Three facts, because no one of them answers the question. **Build** is the commit Cloudflare built
from and changes every deploy. **Cache** is read from the *running* service worker rather than from
source — a device serving a stale bundle has the stale worker too, so asking the worker is the
difference between what should be installed and what is. **Version** is last, because
`package.json` only changes when somebody bumps it.

`CF_PAGES_COMMIT_SHA` has no `VITE_` prefix so Vite will not expose it on its own; injected via
`define`. Verified end to end by building with the variable set and grepping the bundle for it.
eslint gains two *scoped* blocks — node globals for `vite.config.js`, the injected constants for
`buildInfo.js` — rather than loosening globals everywhere.

## BTL-B26 — stopped. The privacy copy does not match the app

The spec carries a finished plain-English explainer and a full legal policy, and the job was meant
to be rendering them at `/privacy`. Checked the claims against the code first. **Four are not true:**

| The copy says | The app |
|---|---|
| A whole **Share links** section — pick what to share, 7-day expiry, revoke from settings | No such feature exists anywhere in `src/` |
| *"Delete your account and all associated data from Settings"* | No deletion exists at all |
| *"full data export — coming soon"* | Shipped: Settings › Data › Export JSON |
| — nothing about friend codes or the public profile | Both exist and are the sharing that really happens |

A privacy policy is a legal statement about what the software does. Publishing one that describes a
feature that does not exist, omits the sharing that does, and promises a deletion route with no
implementation is not a thing to ship and tidy afterwards. **So the page was not built** — B26 is
blocked on B31 (Ben settles the wording; it is a statement about his service, not a code change) and
B32 files the missing deletion capability.

The spec's own TODO list anticipated half of it: *"Data export — referenced in the policy as 'coming
soon'. Must ship before the policy states it is available."* It shipped; nobody came back to the
policy. Exactly the drift B25 above now guards against.
