## SDLC re-baselined to two stages

Ben asked to re-baseline the SDLC — "what it is and what it should be" — after the branch model kept

### What it actually was

The documented `feature → preprod → main` flow **had never run once**. `preprod` points at
`add5889`, which is a commit in `main`'s own linear history dated 2026-08-10 — so the branch was
created by pointing at `main`'s tip and then never used. It never received a merge and was never
merged into `main`. `main`'s history is linear throughout, with no merge commits since 2026-07-12.

So yesterday's two "deviations from the branching model" weren't deviations. Direct-to-`main` is the
only mode this repo has ever had.

### What it is now

Two stages: **feature branch → `main`**. Rewrote `docs/guides/betalog_sdlc.md` and the Branches
section of `CLAUDE.md` to match.

The argument for dropping the middle stage, recorded in the guide so it doesn't get re-litigated:
Cloudflare Pages builds a preview URL for *every* branch, so verification on a real URL already
happens one stage earlier — `preprod` added no capability. A staging branch earns its place when
several people land work independently and a release needs a batching point. What actually protects
production here is the pre-merge checklist plus Cloudflare's instant rollback, and neither needs an
extra branch. Noted that if the third stage ever comes back it should come back with CI, or it will
drift the same way.

Also folded into the guide: `npm run lint` in the checklist, the Worker deploy step
(`workers/betalog-calendar/`), and the fact that Firestore rules do **not** ship with a merge to
`main` — a separate `firebase deploy` is required.

## iOS alarm didn't fire — trigger rewritten to Apple's own form

Ben set a reminder for 09:05, then retested at ~12:30 with silent mode off. The event appears in the
Calendar app both times; the alarm fired neither time.

### Ruled out

- **Silent mode.** Present in the first test (bell-slash in the status bar), off in the second. Still
  no alert, so this was not it.
- **Refresh lag.** iOS picked up the moved event time almost immediately, so the feed is reaching the
  device promptly.
- **Malformed output.** Rendered the feed for a two-entry schedule and inspected every line with its
  octet count. No folding damage, no stray CRLF, `VALARM` correctly nested inside `VEVENT`, and all
  three properties `ACTION:DISPLAY` / `TRIGGER` / `DESCRIPTION` present — Apple silently drops alarms
  missing `DESCRIPTION`, so that was worth confirming.
- **Calendar settings.** "Event Alerts" is on for the subscribed calendar.

### The change

That leaves the trigger encoding. We were emitting:

```
TRIGGER;RELATED=START:PT0S
```

Valid RFC 5545, and the same instant Apple means by "at time of event" — but not how Apple writes it.
Apple's own exports use the negative zero-duration form with no explicit `RELATED`, since `START` is
the default:

```
TRIGGER:-PT0S
```

Changed to match, and added a stable per-entry `UID` inside the `VALARM` (Apple emits one; RFC 9074
sanctions it). Both are byte-level conformance changes — the alarm still fires at the chosen time,
so yesterday's decision against a `-PT10M` lead is untouched.

The offset is now a named constant `ALARM_TRIGGER` at the top of the alarm section, so the next step
on the ladder is a one-line change.

### If it still doesn't fire

The ladder, in order:

1. `-PT1M` — a small non-zero lead. If that fires and `-PT0S` didn't, the zero duration itself is
   what the parser rejects, and the fix is to pick the smallest lead that works.
2. If a non-zero lead doesn't fire either, this is an iOS limitation on alarms in *subscribed*
   calendars rather than anything in the feed, and no encoding change will fix it. **Route B (web
   push)** — deferred in `docs/specs/betalog_reminders_spec.md` — becomes the real answer, with the
   calendar feed staying as the visible-schedule half.

Worth being straight about the confidence here: step 1 of the ladder is a hypothesis, not a
diagnosis. The feed is provably well-formed, so the fault is in how iOS treats what we send, and
from this side that can only be narrowed by changing one thing and retesting on the device.

### Verified

`npm test` 114/114 (the `ics.test.js` alarm case now asserts the new form and that `RELATED=START` is
gone), `npm run build` clean, `npm run lint` 0 errors / 16 pre-existing warnings. Re-rendered the
feed and confirmed the emitted block.

**Needs a release to test** — the `.ics` is rendered client-side, so this has to reach `main` and be
refetched by iOS before the next attempt means anything.

## The real cause: iOS "Remove Alerts" strips every VALARM

The `-PT0S` change was released and the alarm still didn't fire. Ben then found it in
**Subscription Details → Remove Extra Items → Remove Alerts**, which iOS had set **ON**:

> Strip alerts or attachments from data added to the subscription calendar by the data provider.
> Default alerts will still apply according to your settings.

That is iOS deleting our `VALARM` as the feed is ingested. It explains every observation: the events
render perfectly, "Event Alerts" is on at the calendar level, a normal invite alerts fine, and no
alarm from the feed ever fires regardless of how the trigger is written.

**My trigger-encoding theory was wrong.** `TRIGGER;RELATED=START:PT0S` was never the problem; the
alarm was being discarded before anything parsed it. Worth recording *why* it was wrong rather than
just that it was: I reasoned from the feed outward — proved the `.ics` well-formed, ruled out silent
mode and refresh lag, and concluded the remaining variable must be how Apple parses what we send. The
variable I hadn't enumerated was iOS transforming the feed on ingest, which no amount of inspecting
our own output would ever have surfaced. The lesson is to enumerate the *consumer's* settings as
carefully as our own output.

### What was kept, and what was corrected

- **Kept `TRIGGER:-PT0S` and the VALARM `UID`.** Both are equivalent to what they replaced and match
  Apple's own exports, so there is no reason to churn them back. But the comments claiming iOS
  wouldn't fire the old form were a false causal claim and are now rewritten to say plainly that this
  is conformance, not a fix, and to point at the real cause.
- **Same correction in `ics.test.js`.**

### The product finding — this is the important part

**Every iOS user who subscribes hits this.** Nothing in the setup flow mentioned it, so the failure
mode for a new user is: the calendar appears, the sessions appear, and no reminder ever arrives. A
feature that silently does nothing is worse than one that visibly fails.

Added a highlighted note to the Settings calendar section, shown once the feed is enabled, next to
"Subscribe on this device" — states that iOS defaults **Remove Alerts** on, that the sessions will
still appear so the symptom is silent, and gives the exact tap path to fix it.

### Verified

`npm test` 114/114, `npm run build` clean, `npm run lint` 0 errors / 16 pre-existing warnings.
Not driven in a browser — the change is static copy inside an already-rendered section.

**Confirmed on device.** With Remove Alerts off, the alarm fired: a "Glutes!!! — BetaLog"
notification at 13:40, raised by the Calendar app from the subscribed feed. That closes the last
unproven step — Route A now works end to end, from setting a time in Plan through to a reminder on
the phone, and the `-PT0S` trigger form is confirmed working in the process.

The whole chain is now evidenced: app renders the `.ics` → Worker stores it in KV → iOS subscribes
and refetches → Calendar raises the alarm.

## friendCodes enumeration closed

`firestore.rules` granted `allow read` on `friendCodes/{code}` to any authenticated user. In
Firestore `read` is `get` + `list`, so any signed-in user could query the whole collection and walk
away with every friend code and the uid behind it. Narrowed to `allow get`.

**Checked the app first.** Both call sites in `storage.js` are `getDoc` on a known id — the collision
check when generating a code (`:540`) and `lookupFriendCode` (`:593`). There is no collection query
against `friendCodes` anywhere, so `get` alone is sufficient and nothing breaks.

### Proved it rather than reasoning about it

No firebase CLI in the session, but Java is present, so the Firestore emulator runs. Wrote
`betalog-react/scripts/check-firestore-rules.mjs` — 7 assertions covering the lookup that must keep
working, the enumeration that must not, the signed-out cases, and the write rules (re-checked so this
change couldn't have loosened them by accident). All 7 pass.

**Ran the control**: put `allow read` back and re-ran. The enumeration case flips to
`FAIL — Expected request to fail, but it succeeded`, everything else stays green. So the hole was
real and the test actually detects it — a rules test that passes against the broken rule would have
been worthless.

The script is committed but deliberately outside `npm test`: it needs Java and two packages that
aren't project dependencies. Documented in the SDLC guide beside the rules deploy step, with the
instruction to flip the rule and confirm a new case fails before trusting it.
